## 一、Python + FastAPI

### Q1：你们为什么选择 FastAPI 而不是 Flask 或 Django？FastAPI 的哪些特性对你们的项目特别有价值？

**期待答题要点：**
- **异步原生支持：** FastAPI 基于 Starlette，原生支持 `async/await`，对 Agent 场景中大量 I/O 密集型操作（LLM API 调用、工具调用、数据库查询）非常关键
- **自动 OpenAPI 文档：** 自动生成 Swagger/ReDoc，方便前端对接和内部调试
- **类型校验：** 基于 Pydantic 的请求/响应模型自动校验，减少手写校验逻辑
- **性能：** 基于 Uvicorn (ASGI)，性能接近 Node.js/Go，适合高并发的 Agent 服务

**追问（循序渐进）：**

- FastAPI 的中间件和依赖注入有什么区别？你们在什么场景下用中间件？
- FastAPI 的后台任务（BackgroundTasks）你们用过吗？和异步任务队列有什么区别？

---

**我的回答：**

**选型理由**（结合 `app/main.py` 和 `app/config.py` 实际代码）：

1. **异步原生支持**：Agent 场景大量 I/O 密集型操作（LLM API 调用、工具调用、数据库查询），FastAPI 基于 Starlette 原生支持 `async/await`
2. **自动 OpenAPI 文档**：`app/api/` 下有 21 个路由模块（agents、chat、tools、traces、channels、knowledge、memories、sessions、skills、teams 等），FastAPI 自动生成 Swagger 文档，前端对接效率极高
3. **类型校验**：基于 Pydantic 的请求/响应模型（如 `ChatTurnRequest`、`ToolCreateRequest`）自动校验，减少手写校验逻辑
4. **性能**：基于 Uvicorn (ASGI)，适合高并发的 Agent 服务场景

**追问回答**：

- **依赖注入系统**：

  - 与 Celery 的区别：无需外部依赖（Redis/RabbitMQ），适合单机部署场景；重量级任务（如记忆提取、知识入库）都通过 `async_jobs` 队列处理

```python
    request: ChatTurnRequest,

    db: Session = Depends(get_session),

    # 工作线程执行 Agent 循环，将事件写入数据库
    # 中继线程轮询数据库，将事件以 SSE 格式推送给前端
    ...
```

**流式架构**（线程中继模式）：
1. `run_stream_worker()` 在后台线程中执行 `AgentLoop(worker_db).handle_turn_stream(request)`，将执行事件（stream_delta、tool_result、knowledge_result 等）持久化到数据库
2. `stream_events()` 在主线程中轮询数据库，将事件以 SSE 格式推送给前端
3. 关键参数：`STREAM_CHUNK_INTERVAL_SECONDS = 0.045`（chunk 间隔）、`STREAM_RELAY_POLL_SECONDS = 0.08`（轮询间隔）、`STREAM_RELAY_HEARTBEAT_SECONDS = 5.0`（心跳间隔）

- 通过 `HarnessExecutionCancelled` 异常机制处理中断
- 中继线程检测到客户端断开后停止轮询，工作线程通过取消信号终止执行

**追问回答**：

- **连接断开感知**：通过中继线程的轮询机制和 `HarnessExecutionCancelled` 异常处理
- **SSE vs WebSocket**：
  - **SSE**：单向通信（服务器→客户端），实现简单，适合流式输出
  - **WebSocket**：双向通信，适合实时交互（如聊天室）
  - **选择 SSE**：Agent 场景主要是服务器推送结果，不需要客户端实时发送消息

- **流式输出中的错误处理**：
  - 错误时发送 `error_occurred` 事件
  - 支持 `stream_cancelled`、`stream_interrupted` 等中断事件类型
  - 事件类型包括：`session_created`、`user_message_received`、`stream_delta`、`stream_end`、`stream_replace`、`complete`、`error_occurred`、`stream_cancelled`、`stream_interrupted`、`status`、`tool_result`、`knowledge_result`、`step_result`

### Q3：Python 的 GIL 对你们的项目有什么影响？你们是如何应对的？

**期待答题要点：**
- GIL 限制了 CPU 密集型任务的并行执行，但对 I/O 密集型（LLM API 调用、数据库操作）影响较小
- Agent 执行主要是 I/O 等待（等 LLM 返回），所以 asyncio 协程可以很好地并发
- 如果有 CPU 密集场景（如文本处理、embedding 计算），可以用 `multiprocessing` 或 `concurrent.futures.ProcessPoolExecutor`
- Python 3.11+ 的 asyncio 性能改进（如 `TaskGroup`）是否有使用

**追问：**
- 你们有没有遇到过 GIL 导致的性能瓶颈？具体是什么场景？
- 如果要在同一进程中同时做 embedding 计算（CPU 密集）和 API 服务（I/O 密集），怎么设计？

---

**我的回答：**

**GIL 的影响**：
- **CPU 密集型任务**：GIL 限制并行执行（如文本处理、embedding 计算）
- **I/O 密集型任务**：GIL 影响较小（如 LLM API 调用、数据库查询）

**Agent 场景的特点**：
- 主要是 I/O 等待（等 LLM 返回、等工具调用结果）
- `asyncio` 协程可以很好地并发

**应对措施**：

1. **多线程并发**：
   - 使用 `ThreadPoolExecutor` 处理异步任务（如 `AsyncJobQueue`）
   - 流式响应采用线程中继模式（工作线程 + 中继线程）
   - 多个渠道适配器（飞书、钉钉）可以并发处理消息

2. **CPU 密集场景的处理**（理论方案，项目当前未实现）：
   - 如果未来需要 embedding 计算，可以使用 `ProcessPoolExecutor` 将 CPU 密集任务放到独立进程
   - 或者将 embedding 服务独立部署，通过 HTTP API 调用

3. **Python 3.11+ 的改进**：
   - 项目使用 Python 3.11+，受益于 asyncio 性能优化
   - 当前主要使用同步的 `httpx.Client` 和 SDK 调用，GIL 影响有限

**追问回答**：

- **GIL 性能瓶颈**：当前项目主要是 I/O 密集型（LLM API 调用、数据库查询、工具调用），GIL 影响较小
- **同时做 embedding 和 API 服务**（理论方案）：
  - 方案一：embedding 计算放到独立进程（`ProcessPoolExecutor`）
  - 方案二：embedding 服务独立部署，通过 HTTP API 调用
  - 方案三：使用多线程（`ThreadPoolExecutor`），利用 I/O 等待时释放 GIL

## 二、SQLite

### Q4：你们为什么选择 SQLite 而不是 PostgreSQL 或 MySQL？在什么场景下 SQLite 会成为瓶颈？

**期待答题要点：**
- **选型理由：** 部署简单（单文件、无需独立服务）、适合单机/桌面部署场景、降低运维成本
- **已知限制：** 写并发受限（单写者锁）、不支持多机分布式、缺少部分高级特性（如细粒度权限控制、JSON 查询能力有限）
- **应对措施：** WAL 模式实现读写并发、busy_timeout 等待写锁释放
- 能说出在什么数据量级或并发量级下需要考虑迁移到 PostgreSQL

**追问（循序渐进）：**
- SQLite 的 WAL 模式是什么？和普通 Journal 模式有什么区别？
- 你们如何处理 SQLite 的并发写入冲突？有没有遇到 `database is locked` 错误？
- SQLite 的 JSON 字段你们用过吗？查询性能如何？
- 如果要从 SQLite 迁移到 PostgreSQL，你们的 ORM/数据访问层需要做哪些改动？

---

**我的回答：**

**选型理由**（结合 `app/config.py` 和 `app/db/database.py` 实际代码）：
1. **部署简单**：单文件数据库，无需独立服务，`database_url: str = "sqlite:///./skill_agent_loop.db"`
2. **适合单机/桌面部署**：StaffDeck 初期定位为单机部署场景
3. **降低运维成本**：无需维护 PostgreSQL/MySQL 集群

**已知限制**：
1. **写并发受限**：单写者锁，高并发写入时性能下降
2. **不支持多机分布式**：无法水平扩展
3. **缺少高级特性**：如细粒度权限控制、JSON 查询能力有限

**应对措施**：
1. **WAL 模式**：
   ```python
   # app/db/database.py
   engine = create_engine(
       database_url,
       connect_args={"check_same_thread": False},
       pool_pre_ping=True,
   )
   # 启用 WAL 模式
   with engine.connect() as conn:
       conn.execute(text("PRAGMA journal_mode=WAL"))
   ```

2. **busy_timeout 配置**：
   ```python
   conn.execute(text("PRAGMA busy_timeout=30000"))
   ```
   当遇到写锁时，SQLite 会等待最多 30 秒而非立即报错

3. **WAL 模式下的读写并发**：
   - 读操作：多个连接并发读取（不受写操作阻塞）
   - 写操作：单写者锁，但通过 busy_timeout 等待而非立即失败

**迁移到 PostgreSQL 的时机**：
- 并发用户数 > 100
- 日均消息量 > 10 万
- 需要多机分布式部署

**追问回答**：

- **WAL 模式 vs Journal 模式**：
  - **Journal 模式**：写操作先写日志文件，再写数据文件，写锁持有时间长
  - **WAL 模式**：写操作先写 WAL 文件，读操作可以并发读取数据文件，写锁持有时间短

- **并发写入冲突**：
  - 遇到过 `database is locked` 错误
  - 解决：启用 WAL 模式 + 写操作队列串行化

- **JSON 字段**：
  ```python
  # SQLite JSON 查询
  from sqlmodel import select
  
  # 查询 content_json 中包含特定字段的记录
  statement = select(Skill).where(
      text("json_extract(content_json, '$.nodes') IS NOT NULL")
  )
  ```
  - 查询性能：比 PostgreSQL 的 JSONB 慢，但对于小规模数据（< 10 万条）可接受

- **迁移到 PostgreSQL 的改动**：
  - ORM 层：SQLModel 同时支持 SQLite 和 PostgreSQL，无需改动
  - 数据迁移：使用 Alembic 做 schema 迁移
  - 性能优化：利用 PostgreSQL 的 JSONB、索引等特性

## 三、MCP（Model Context Protocol）

### Q6：请解释一下 MCP 协议的核心概念。它在你们的项目中扮演什么角色？

**期待答题要点：**
- MCP 是 Anthropic 提出的标准化协议，用于 LLM 与外部工具/数据源的交互
- 核心概念：MCP Server（提供 tools/resources/prompts）、MCP Client（Agent 侧调用）、Transport（stdio/SSE/HTTP）
- 在项目中用于统一接入外部工具：Agent 通过 MCP 协议发现和调用各种业务系统的工具
- 能说出 MCP 相比直接 HTTP 调用的优势：标准化工具发现、统一的参数描述、协议级别的安全控制

**追问（循序渐进）：**
- MCP 的 Transport 层你们用了哪种？stdio 和 SSE 各有什么优缺点？
- MCP Server 的工具发现机制是怎样的？Agent 如何知道有哪些工具可用？
- 如果一个 MCP Server 挂了，Agent 执行过程中如何处理？有没有重试和降级机制？
- MCP 和 OpenAI 的 Function Calling 有什么异同？你们为什么选了 MCP？

---

**我的回答：**

**MCP 协议核心概念**（结合 `app/tools/mcp_client.py` 实际代码）：

MCP（Model Context Protocol）是 Anthropic 提出的标准化协议，用于 LLM 与外部工具/数据源的交互。

- **MCP Server**：提供 tools/resources/prompts 的服务
- **MCP Client**：Agent 侧调用 MCP Server 的客户端
- **Transport**：通信方式（stdio/SSE/HTTP）

**在项目中的角色**：
- 用于统一接入外部工具
- Agent 通过 MCP 协议发现和调用各种业务系统的工具

**相比直接 HTTP 调用的优势**：
1. **标准化工具发现**：MCP Server 自动暴露可用工具列表
2. **统一的参数描述**：工具参数用 JSON Schema 描述
3. **协议级别的安全控制**：MCP 协议内置权限校验机制

**追问回答**：

- **Transport 层选择**（从 `mcp_client.py` 的 `normalize_transport` 提取）：
  ```python
  def normalize_transport(config: dict[str, Any]) -> str:
      raw = str(config.get("transport") or "").strip().lower()
      if raw == "streamable_http":
          return "http"
      if raw:
          return raw
      server = str(config.get("server") or config.get("server_id") or "").strip()
      if server == "builtin.demo":
          return "builtin"
      if config.get("command"):
          return "stdio"
      if config.get("url") or config.get("endpoint"):
          return "http"
      return "builtin"
  ```
  - **stdio**：适合本地进程间通信，延迟低，但只能本地使用
  - **SSE/HTTP**：适合远程通信，支持流式返回
  - **builtin**：内置 MCP 工具，无需外部进程

- **工具发现机制**：

### Q10：ReAct（Reasoning + Acting）模式在你们的项目中是如何实现的？

**期待答题要点：**
- ReAct 核心循环：Thought → Action → Observation → Thought → ...
- 实现方式：LLM 输出结构化的思考-行动对 → 解析 Action → 执行工具 → 将 Observation 注入上下文 → 继续下一轮
- 终止条件：LLM 输出 Final Answer 或达到最大轮次

**我的回答：**

**ReAct 核心循环**（从 `app/core/harness_agent.py` 的 `HarnessTaskAgent` 提取）：

```python
class HarnessTaskAgent:
    """隔离执行单个 TaskRequirement"""
    
    def run(self, requirement, session, checkpoint=None, ...):
        # 支持检查点恢复：从上次中断的位置继续
        if checkpoint:
            self._restore_from_checkpoint(checkpoint)
        
        while not self._is_done():
            # 步骤超时控制
            if self._step_deadline_exceeded():
                return self._step_timeout_result()
            
            # 构建 prompt：包含当前 SOP 节点状态、可用工具、知识上下文、最近任务摘要
            stage_data = {
                "active_skill": active_skill,
                "retrieved_knowledge": compact_knowledge,
                "router_decision": compact_step_router_decision(...),
                "slots": _step_agent_slots(session.slots_json),
                "awaiting_input": compact_awaiting_input(...),
                "available_tools": available_tools,
                "recent_task_summaries": self.recent_task_summaries,  # 新增：最近任务摘要作为记忆
            }
            
            # LLM 输出结构化动作序列（支持批量动作）
            raw = self._generate_harness_action_json(stage_data)
            actions = self._harness_actions_from_raw(raw)  # 返回 list[HarnessAction]
            
            # 检查必需能力是否已调用
            if self._missing_required_capabilities(actions):
                return self._failure("REQUIRED_CAPABILITY_NOT_INVOKED")
            
            # 执行动作（工具调用/完成）
            for action in actions:
                if action.kind == "tool":
                    result = self._invoke_capability(action)
                    self._save_checkpoint()  # 每步保存检查点
                elif action.kind == "finish":
                    return self._finish_result(action)
```

**远程更新新增特性**：
1. **检查点恢复**：`checkpoint` 参数支持从 `task_frame_id`/`step_id` 匹配恢复，服务重启后不丢失执行进度
2. **批量动作序列**：`_harness_actions_from_raw()` 返回 `list[HarnessAction]`，单次 LLM 输出可包含多个动作，减少轮次
3. **步骤超时控制**：`step_deadline_monotonic` + `step_timeout_seconds`，防止单个步骤无限阻塞
4. **必需能力检查**：`_missing_required_capabilities()` 确保关键能力被调用后才允许完成
5. **非重试失败签名**：`non_retryable_action_signatures` 不再跨回合继承失败
6. **最近任务摘要**：`recent_task_summaries` 作为 AgentLoop 记忆，提升上下文连贯性
7. **协议修复重试**：2 次尝试修复 LLM 输出格式偏差

**终止条件**：
1. LLM 输出 `finish` 动作（最终回复）
2. 达到最大轮次（`harness_max_actions`，默认 32，最大 100）
3. 步骤超时（`step_timeout_seconds`）
4. 必需能力未调用（`REQUIRED_CAPABILITY_NOT_INVOKED`）

**与其他 Agent 模式的区别**：
- **ReAct**：逐步推理，每步都调用 LLM，适合需要动态决策的场景
- **Plan-and-Execute**：先规划完整计划，再逐步执行，适合确定性强的场景
- **LATS**：树搜索，探索多条路径，适合需要最优解的场景

**追问回答**：

- **无效 Action 的处理**（从 `HarnessCapabilityInvoker.invoke` 提取）：
  ```python
  # 工具名不存在
  registered = self.registry.get(call.name)
  if registered is None:
      return self._failure(call, HarnessToolError(
          code="TOOL_NOT_FOUND",
          message=f"Harness tool is not registered: {call.name}",
      ))
  
  # 参数格式错误
  ```

- **最大轮次**：默认 32（`harness_max_actions`），最大 100（`MAX_TOOL_ACTIONS_PER_TURN_LIMIT`）

- **Thought 部分展示**：不展示给用户，只展示最终回复

- **Function Calling vs ReAct**：
  - **Function Calling**：OpenAI 提供的结构化输出，直接输出工具调用
  - **ReAct**：更灵活，支持思考过程、知识检索、多轮推理
