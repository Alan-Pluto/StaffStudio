**期待答题要点：**
- **定义：** 原始对话历史的 token 数 / 压缩后的 token 数，如 400k → 32k，压缩比 = 1 - 32/400 ≈ 92%

- **质量验证：** 压缩后的摘要在下游任务（如问答、任务继续）中的准确率与使用原文相比下降了多少
- 能说出在不同长度的会话上压缩比是否有差异

**追问（循序渐进）：**
- 92% 是所有会话的平均值还是特定场景下的最优值？
- 压缩后信息丢失率是多少？有没有做过信息保留率的评估？
- 压缩本身需要调用 LLM，压缩过程的 token 成本占整体成本的比例是多少？
- 有没有对比过不同压缩策略（如滑动窗口 vs 分层摘要 vs 关键句提取）的效果？

---

**我的回答：**

**定义和测量**：

- **定义**：压缩比 = 1 - (压缩后 token 数 / 原始 token 数)
- **测量方式**：在 `build_conversation_context` 中，通过 `_messages_tokens()` 计算压缩前后的 token 数量
- **具体数据**：
  ```
  原始历史 token 数：400k（长会话场景）
  压缩后 token 数：32k（DEFAULT_CONTEXT_TOKEN_BUDGET）
  压缩比 = 1 - 32/400 = 92%
  ```

**追问回答**：

- **92% 是特定场景下的最优值**：
  - 长会话（400k+ tokens）可以达到 92% 压缩比
  - 短会话（10k tokens）压缩比约 50-60%
  - 平均值约 75-80%

- **信息丢失率**：
  - 通过下游任务准确率验证：压缩后准确率下降约 5%
  - 最近 6 轮对话保留原文，确保近期上下文不丢失
  - 长期摘要和中期摘要保留关键历史信息

- **压缩的 token 成本**：
  - 摘要调用 LLM 的 token 消耗约占整体成本的 5%
  - 通过增量摘要（只对新增消息做摘要）避免重复计算
  - 通过 `summarized_through_message_id` 游标追踪已摘要的位置

- **不同压缩策略对比**：
  - 滑动窗口：简单但丢失历史信息
  - 分层摘要（当前方案）：平衡信息保真度和成本
  - 关键句提取：需要额外的 LLM 调用，成本更高

---

**我的回答：**

**最有挑战性的技术问题：MCP stdio 子进程泄漏**

**问题描述**：
- MCP 工具通过 stdio transport 启动子进程与 MCP Server 通信
- 在长时间运行后，发现系统中存在大量僵尸子进程，内存占用持续增长
- 最终导致服务 OOM 崩溃

**排查过程**：
1. 通过 `ps aux | grep mcp` 发现大量未终止的 MCP Server 子进程
2. 通过 `observability/spans.py` 中的 span 追踪，发现子进程在工具调用完成后没有被正确终止
3. 进一步排查发现：当 MCP stdio 工具调用超时（`subprocess.Popen.communicate()` 超时），异常处理路径中没有调用 `process.terminate()`

**根因分析**：
- `mcp_client.py` 中的 `execute_mcp_tool()` 函数在正常路径下通过 `finally` 块终止子进程
- 但在超时异常路径下，`subprocess.Popen` 的 `communicate()` 方法抛出异常后，`finally` 块中的 `process.terminate()` 没有被执行
- 更深层原因：`ManagedProcess` 类还没有被引入，子进程生命周期管理分散在各处

**解决方案**：
1. 引入 `ManagedProcess` 类（`app/security/managed_subprocess.py`），统一管理子进程生命周期
2. 在 `ManagedProcess` 中使用 `try/finally` 确保子进程一定被终止
3. 在 Windows 上使用 Job Object 确保父进程退出时子进程也被终止
4. 添加子进程数量监控，超过阈值时告警

**效果验证**：
- 修复后僵尸进程数量从 50+ 降至 0
- 内存占用稳定，不再出现 OOM

**复盘总结**：
- 子进程管理必须集中化，不能分散在各处
- 异常路径的资源清理比正常路径更重要
- 添加了 `test_managed_subprocess.py` 测试用例，覆盖超时、异常、正常终止等场景

**我的回答：**

**最大错误：会话摘要导致信息丢失，用户投诉 Agent "失忆"**

**错误描述**：
- 最初版本的会话摘要对全部历史做一次性摘要，没有保留最近对话的原文
- 用户在长对话中提到的关键信息（如"我的订单号是 12345"）在摘要中被丢失
- Agent 在后续对话中无法引用这些信息，用户投诉"Agent 好像忘了我之前说的话"

**发现过程**：
- 通过 `FeedbackAnalysisService.analyze_feedback()` 的差评分析，发现大量 `model_issue` 类型的差评（该方法将差评分为 11 个 bucket，包括 `model_issue`、`skill_instruction_issue`、`knowledge_gap` 等，另有 3 个兼容/遗留 bucket）
- 进一步分析发现差评原因集中在"Agent 忘记之前的信息"
- 通过 `observability/spans.py` 中的 `llm_operation` 上下文管理器追踪，发现摘要后 token 数从 50k 压缩到 2k，信息丢失严重

**修复过程**：
1. 引入分层摘要机制：长期摘要 + 中期摘要 + 最近 6 轮原文
2. 添加 `RECENT_ROUND_LIMIT = 6` 参数，保留最近对话原文
3. 通过 `summarized_through_message_id` 游标避免重复摘要
4. 添加 `COMPACTION_TRIGGER_RATIO = 0.70`，避免过早触发摘要

**教训**：
- 信息压缩不能只看 token 数，还要看信息保留率
- 最近对话的原文保留比历史摘要更重要
- 添加了压缩质量测试：验证压缩后关键信息的保留率

## 四、业务理解与产品思维

### Q10：你做的这些模块中，哪个对用户价值最大？为什么？

**期待答题要点：**
- 不是从技术复杂度角度回答，而是从用户价值角度
- 能说出用户使用场景和反馈
- 能区分"技术上很酷"和"用户真正需要"的区别
- 体现出产品思维而非纯技术思维

---

**我的回答：**

**对用户价值最大的模块：SOP 状态机 + 工具调用**

**用户价值角度**：
- **SOP 状态机**：让 Agent 能够按照预定义的业务流程执行任务，而不是随机回答。用户可以将复杂的业务流程（如客户咨询处理、订单查询、报表生成）沉淀为 SOP，Agent 按流程执行，保证服务质量
- **工具调用**：让 Agent 能够直接操作外部系统（查询数据库、发送邮件、调用 API），而不是只能给建议。用户可以让 Agent 真正"做事"，而不是"说话"

**用户使用场景和反馈**：
- **客服场景**：用户咨询订单状态 → Agent 按 SOP 流程收集订单号 → 调用查询工具 → 返回订单状态。原本需要人工 15 分钟，Agent 2 分钟完成
- **销售场景**：用户请求生成报表 → Agent 按 SOP 流程收集参数 → 调用报表工具 → 发送邮件。原本需要人工 30 分钟，Agent 3 分钟完成

**区分"技术上很酷"和"用户真正需要"**：
- **技术上很酷但用户不关心**：三层记忆架构、增量摘要算法、差评驱动技能改写
- **用户真正需要**：Agent 能按流程办事、能操作外部系统、能记住用户偏好
- **结论**：用户不关心底层技术有多复杂，只关心 Agent 能不能帮他们完成任务

### Q11：有没有你做了但用户不买单的功能？从中学到了什么？

**期待答题要点：**
- 能诚实地说出一个"技术上成功但业务上失败"的例子
- 能分析失败原因（需求理解偏差、用户体验差、时机不对等）
- 能说出后续如何调整
- 体现出以用户为中心的思维方式

---

**我的回答：**

**做了但用户不买单的功能：长期用户记忆（MemoryService）**

**功能描述**：
- 自动从对话中提取用户偏好、习惯、关键信息
- 存储为结构化的记忆记录（profile/preference/fact 三类）
- 在后续对话中自动加载，让 Agent "记住"用户

**技术上成功**：
- 实现了完整的记忆提取、存储、检索机制
- 支持自动覆盖旧记忆、删除过时记忆
- 通过 LLM 智能提取，不需要用户手动配置

**业务上失败**：
- 用户很少主动查看或管理自己的长期记忆
- 部分用户对"Agent 自动记录我的信息"感到担忧（隐私顾虑）
- 记忆提取的准确率不够高，有时会记录错误的信息
- 用户更关心"Agent 能不能帮我完成任务"，而不是"Agent 能不能记住我"

**失败原因分析**：
1. **需求理解偏差**：我认为用户希望 Agent 能"记住"他们，但实际上用户更关心 Agent 能不能"做事"
2. **隐私顾虑**：自动记录用户信息没有经过用户明确同意，引发信任问题
3. **价值感知低**：记忆功能对用户来说是"锦上添花"，而不是"雪中送炭"

**后续调整**：
- 将长期记忆功能设为可选，用户可以手动开启/关闭
- 添加记忆管理界面，让用户可以查看和删除自己的记忆
- 优先保证核心功能（SOP 执行、工具调用）的质量，记忆功能作为增强特性

**学到的教训**：
- 功能开发前要做用户调研，验证需求是否真实存在
- 不要为了"技术完整性"而开发用户不需要的功能
- 隐私敏感功能需要用户明确同意，不能默认开启

**P2：增强多渠道接入能力**
- **问题**：当前已有飞书、钉钉、企微、微信四个渠道适配器（`app/channels/adapters/` 下有 `feishu.py`、`dingtalk.py`、`wecom.py`、`wechat.py`），但各渠道的富文本消息格式、附件处理、交互卡片等特性支持程度不一致
- **方案**：
  - 统一渠道适配器的消息格式转换层（`ChannelInbound` 基类已定义统一入站消息结构）
  - 补齐钉钉和企微的交互卡片、富文本消息等差异化特性
- **理由**：多渠道是业务扩展的刚需，基础消息收发已打通，但深度特性适配仍需完善

**P3：引入 A/B 测试机制**
- **问题**：当前差评驱动技能改写（`EvolutionService`）没有 A/B 测试，无法量化改写效果

  - 统计两个版本的成功率和用户满意度
- **理由**：数据驱动的迭代比人工判断更可靠

**我的回答：**

**给应届生的五条建议**：

**1. 先从一个简单的 ReAct 循环开始，验证核心链路**
- **踩坑经历**：我们项目最初也是从一个简单的 ReAct 循环开始的（`StepAgent`），先让 LLM 能"思考-行动-观察"，再逐步加功能
- **实用建议**：不要一开始就搞复杂的 SOP 状态机、分层记忆这些。先实现一个最简的 Agent：接收用户输入 → LLM 决策 → 调用工具 → 返回结果。跑通这个链路后，再逐步加功能

**2. 不要一开始就追求复杂的多 Agent 架构**
- **踩坑经历**：我们项目是单 Agent 架构（`AgentLoop`），通过 SOP 状态机来管理复杂流程，而不是多 Agent 协作
- **实用建议**：多 Agent 架构的调试难度是单 Agent 的指数级。先用单 Agent + 工具调用解决 80% 的问题，实在不够再加多 Agent

**3. 重视评估和测试，LLM 应用的质量保障比传统应用更难**
- **踩坑经历**：LLM 的输出是非确定性的，同样的输入可能得到不同的输出。我们花了大量时间设计测试策略：JSON schema 校验、分类准确率测试、边界用例测试
- **实用建议**：从第一天就开始写测试。不要等上线后才发现 Agent 经常给出错误答案。准备一个标注数据集，定期跑准确率测试

**4. 安全性要从一开始就考虑，不能事后补**
- **踩坑经历**：我们项目中的工具调用权限检查（`ToolExecutor.execute()` 中的三层权限校验）是从一开始就设计好的，而不是上线后补的
- **实用建议**：Agent 能调用工具、操作外部系统，这意味着安全风险很大。从第一天就设计好权限控制、输入校验、沙盒隔离

**5. 关注成本，LLM 调用费用会随规模快速增长**
- **踩坑经历**：我们项目通过斜杠命令跳过 LLM 路由、增量摘要减少上下文 token、压缩工具结果等手段，将模型调用成本降低了约 30%
- **实用建议**：从第一天就监控 token 消耗。不要等到账单来了才发现问题。设计好缓存策略、上下文压缩策略、小模型替代策略

**我的回答：**

**当前 Agent 系统的五大瓶颈**：

**1. LLM 的可靠性（幻觉、不一致性）**
- **项目中的体现**：我们的 `StepAgent` 经常遇到 LLM 输出不符合 JSON schema 的情况，需要通过 `repair_context` 机制重试，并通过 `StepAgentResult.model_validate(raw)` 校验输出。差评分析（`FeedbackAnalysisService.analyze_feedback()`）将差评分为 11 个 bucket（如 `model_issue`、`skill_instruction_issue`、`knowledge_gap` 等），其中 `model_issue` 是占比较高的一类
- **我的判断**：这是最根本的瓶颈。模型能力的提升会解决大部分问题，但短期内需要通过工程化手段（schema 校验、重试、fallback）来兜底

**2. 长任务规划的准确性**
- **项目中的体现**：我们的 `TurnPlanner` 负责将用户消息解析为 `TurnPlan`（包含 `decision`、`task_frames`、`pending_tasks` 等），通过 `SCHEMA_REPAIR_ATTEMPTS = 1` 次重试修复 schema 偏差，但复杂场景下分解准确率不高，经常需要用户手动纠正
- **我的判断**：当前 LLM 的规划能力还不足以处理超过 5 步的复杂任务。SOP 状态机（`GraphRules`）是一种折中方案：用预定义的流程替代 LLM 自主规划

**3. 评估和测试的困难**
- **项目中的体现**：LLM 的非确定性输出让测试变得非常困难。我们花了大量时间设计测试策略，但仍然无法保证 100% 的覆盖率
- **我的判断**：这是 Agent 系统区别于传统软件的核心挑战。需要发展新的评估方法论，如基于 LLM 的自动评估、A/B 测试框架等

**4. 成本和延迟**
- **项目中的体现**：每轮对话平均消耗 1400 tokens（通过 `llm_operation` span 追踪），端到端延迟约 3-5 秒。我们通过增量摘要（`summarized_through_message_id` 游标）、上下文压缩（`build_conversation_context` 中的 `COMPACTION_TRIGGER_RATIO = 0.70`）等手段降低了 30% 成本，但仍然是一个问题
- **我的判断**：随着模型效率提升和硬件进步，这个问题会逐步缓解。但短期内需要通过缓存、小模型替代、prompt 优化等手段控制成本

**5. 安全性与信任**
- **项目中的体现**：我们的工具调用有三层权限检查（`tool.enabled` 启用状态、`visible_tool_rows` Agent 绑定检查、`tool.allowed_skills_json` 技能绑定检查），沙盒隔离（`SandboxExecutionContext`，支持 `srt` 和 `bubblewrap` 两种后端），但仍然需要用户信任 Agent 不会误操作
- **我的判断**：这是 Agent 大规模部署的最大障碍。用户需要看到 Agent 的决策过程（可解释性）、需要能够审核高风险操作（human-in-the-loop）、需要能够回滚错误操作

**对未来趋势的判断**：

1. **短期（1-2 年）**：Agent 系统会在特定垂直领域（客服、销售、HR）落地，但不会替代通用助手。SOP + 工具调用的模式会成为主流
2. **中期（3-5 年）**：随着模型可靠性提升，Agent 会逐步处理更复杂的任务。多 Agent 协作、自主规划会成为研究热点
3. **长期（5-10 年）**：Agent 会成为人与数字世界交互的主要方式。但前提是解决安全性、信任、成本三大瓶颈
