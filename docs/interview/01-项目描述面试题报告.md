**我的回答：**

StaffDeck 是一个**数字员工平台**，核心定位是将企业专家经验和业务流程沉淀为可 7×24 小时持续运行的自动化 Agent。

**使用场景**：
- **SOP 自动化执行**：将标准操作流程（如请假审批、报销流程）编排为图结构（nodes + edges），Agent 按图结构遍历执行

1. **意图理解能力**：传统 RPA 只能执行预定义流程，StaffDeck 能理解用户自然语言意图，自动路由到合适的 Agent
2. **自主决策**：Agent 具备 LLM 推理能力（通过 `StepAgent` 实现），可根据上下文动态选择工具和执行路径
3. **持续进化**：通过用户反馈驱动技能改写，Agent 能力可持续迭代

**追问回答**：
- **与 UiPath 的区别**：UiPath 是流程自动化，需要人工录制流程；StaffDeck 是智能 Agent，能理解意图、自主决策、持续学习
- **数字员工的具体形态**：用户通过 IM 渠道（飞书/钉钉）与数字员工对话，数字员工根据 SOP 流程收集信息、调用工具、返回结果。例如用户说"我要请假"，数字员工会引导填写请假单、查询余额、提交审批

**追问回答**：

### Q3：你提到"基于开源 Agent 编排引擎"，具体是哪个引擎？你们在它的基础上做了哪些扩展和改造？

**期待答题要点：**

- 能说明在引擎之上做了哪些定制化：如状态机 SOP 编排是对引擎原生 DAG 的改造、分层记忆是新增模块、意图路由是自建等

**追问（验证真实性）：**

- 你们有没有给开源项目贡献过代码？有没有遇到引擎的 bug，如何处理的？
- 引擎的哪个设计决策你不太认同？为什么？

---

**我的回答：**

**引擎名称**：Harness v2（自研引擎，调研过 LangGraph/AutoGen 后决定自研）

**选型理由**（为什么不用开源引擎）：
1. **节点级权限控制**：SOP 流程需要每个节点声明可调用的工具白名单，LangGraph/AutoGen 均不支持
2. **多任务帧调度**：用户可能同时发起多个任务（如请假 + 查询余额），需要管理任务间的依赖和切换，开源引擎缺少此概念
3. **可审计性**：每次执行都有完整的 trace 记录（`HarnessRunRecord`、`HarnessInvocationRecord`），满足企业合规要求
4. **Turn 去重与并发控制**：需要跨进程的 session lease 锁和 exactly-once turn receipt，开源引擎不支持

**Harness v2 的三层架构**：

```
HarnessV2Engine
├── TurnPlanner（LLM 任务规划 → 生成 TurnPlan）
├── TaskFrameStore（任务帧持久化与调度）
├── HarnessTaskAgent（隔离执行每个帧）
├── HarnessTurnStore（exactly-once turn 去重）
├── HarnessSessionLeaseStore（跨进程执行锁）
└── CapabilityManifestBuilder（能力发现）
```

**在引擎之上的定制化扩展**：

1. **分层记忆集成**：
   - 在 `HarnessV2Engine` 执行前后注入记忆上下文
   - 对话上下文投影：`ConversationProjection` 负责消息格式化、知识引用去重、附件上下文注入
   - 长期记忆：`MemoryService` 在每轮对话后异步提取用户偏好和事实（`profile`/`preference`/`fact` 三种类型）

2. **意图路由层**：
   - 斜杠命令优先（`parse_slash_command`）：确定性操作不调模型，支持中文别名（/流程、/技能、/工具）
   - `TurnPlanner`：LLM 任务规划，生成 `TurnPlan`（包含 `task_frames` 列表）
   - `Router`：独立 LLM 调用生成 `RouterDecision`，驱动 session 状态变更

3. **工具权限控制**：
   - `GraphRules` 解析 SOP 节点声明的 `allowed_actions`（如 `call_tool:query_balance`、`answer_user`）
   - `_available_tools_for_step()` 在 `StepAgent` 执行前动态构建可用工具列表
   - 防止 Agent 在非授权节点调用敏感工具（如支付接口）

4. **反馈进化闭环**：
   - `FeedbackAnalysisService` 分析差评原因（分类到 11 种 bucket：`model_issue`/`skill_instruction_issue`/`sop_trigger_issue`/`sop_slot_issue`/`sop_transition_issue`/`sop_capability_issue`/`knowledge_gap`/`tool_or_runtime_issue`/`user_random_or_unclear`/`positive_or_resolved`/`unknown`，另外有 3 个兼容/遗留 bucket：`skill_issue`/`tool_or_system_issue`/`needs_model_analysis`）
   - `EvolutionService` 生成技能改写建议（SOP 或 GeneralSkill）
   - 人工审核后更新 SOP 定义，支持回滚

**自研引擎的挑战及解决方案**：

**挑战 1**：SOP 节点级工具权限控制
- **问题**：不同 SOP 节点需要限制可调用的工具（如支付接口只能在特定节点调用）
- **解决方案**：在 `_available_tools_for_step()` 中，从 `current_step.allowed_actions` 提取 `call_tool:<tool_name>`，动态构建可用工具列表

**挑战 2**：对话上下文管理
- **问题**：长对话导致 token 消耗过大，需要压缩历史消息
- **解决方案**：在 `ConversationProjection` 中实现消息投影和压缩，通过 `context_projection.py` 中的 `compact_conversation_context()` 等函数压缩上下文

**挑战 3**：多任务并行管理
- **问题**：用户可能同时发起多个任务（如请假 + 查询余额），需要管理任务间的依赖和切换
- **解决方案**：在 `TaskFrameStore` 中实现任务帧管理，支持任务挂起（`defer_for_action_budget`）、恢复、依赖检查（`dependencies_satisfied`）

**追问回答**：
- **核心抽象**：Harness v2 的核心抽象是 `TurnPlan`（任务规划，包含 `task_frames` 列表）+ `HarnessTaskFrameRecord`（任务帧，包含 `task_id`/`kind`/`decision`/`target_skill_id`/`target_step_id`）+ `RouterDecision`（路由决策）+ `StepAgentResult`（步骤执行结果，包含 `action`/`reply`/`next_step_id`/`slot_updates`）
- **是否贡献过代码**：Harness v2 是自研引擎，非开源项目
- **不认同的设计决策**：Harness v2 的 `ChatSession` 模型承载了太多状态（`slots_json`、`awaiting_input_json`、`active_skill_id`、`active_step_id`、`skill_stack_json`、`pending_tasks_json`、`knowledge_context_json`、`context_state_json`），导致状态管理复杂。如果重新设计，会将会话状态拆分为 `SessionState`（会话级：`status`/`active_skill_id`/`active_step_id`）和 `TaskState`（任务级：`slots`/`pending_tasks`/`skill_stack`）

## 二、核心概念理解

### Q4：你提到"将专家经验、业务流程与决策准则沉淀为可 7×24 持续运行的数字员工"。具体来说，"专家经验"是如何被表示和存储的？

**期待答题要点：**
- 专家经验通过 SOP 文档 → 自动解析为状态机图结构来沉淀
- 决策准则通过节点条件边（条件分支）来编码
- 存储在数据库中（SQLite），包含 SOP 定义、节点配置、工具绑定等
- 能区分"知识"（RAG 检索的文档）和"经验"（SOP 流程定义）的不同存储方式

**追问：**
- 如果业务专家口述了一段流程但没有文档，你们怎么处理？
- SOP 的修改是热更新还是需要重启？版本管理怎么做的？

---

**我的回答：**

**专家经验的表示方式**：

1. **SOP 文档 → 状态机图结构**：
   - 输入：结构化的 SOP 文档（Markdown 或 JSON）
   - 处理：通过 `SkillEditor` 解析为 `Skill` 对象，包含 `content_json`（图结构）
   - 存储：`content_json` 包含 `nodes`（节点列表）和 `edges`（边列表）

2. **节点数据结构**（从 `GraphRules.node_as_step` 提取）：
   ```python
   {
       "step_id": "node_001",
       "node_id": "node_001",
       "type": "step",  # start/step/handoff/end
       "name": "收集请假信息",
       "instruction": "请询问用户请假类型、开始日期、结束日期、请假原因",
       "optional": False,
       "condition": None,  # 进入条件
       "expected_user_info": ["leave_type", "start_date", "end_date", "reason"],
       "allowed_actions": ["call_tool:query_balance", "answer_user"],  # 允许的操作
       "knowledge_scope": {"knowledge_base_ids": ["kb_001"]},  # 知识范围
       "retry_policy": {"max_retries": 3},
       "metadata": {},
        "sub_sop_id": None,  # 子 SOP 嵌套
        "assignee_user_id": None,  # 人工接管处理人
        "assignee_notify_channel": None  # 接管通知渠道
    }
    ```

3. **边数据结构**：
   ```python
   {
       "source_node_id": "node_001",
       "next_node_id": "node_002",
       "condition": "annual_leave",  # 条件标识（default/else/自定义标识）
       "priority": 0  # 优先级（多条件边时，按 priority 排序选择）
   }
   ```

4. **决策准则的编码**：
   - 通过边的 `condition` 字段编码决策分支，条件值为语义标识（如 `default`、`else` 或自定义标识如 `annual_leave`）
   - `StepAgent` 在执行时根据当前上下文（已收集的槽位值）和 LLM 推理，判断应走哪条条件边
   - `GraphRules.outgoing_edges()` 按 `priority` 排序返回出边，`GraphRules.next_steps()` 返回当前节点的所有可能后继

**存储方式**：
- **SOP 定义**：SQLite 的 `skills` 表，`content_json` 字段存储完整图结构
- **节点配置**：嵌入在 `content_json` 中
- **工具绑定**：通过 `tools` 表的 `allowed_skills_json` 字段实现，存储允许调用该工具的 SOP ID 列表。`_sync_skill_tool_bindings()` 函数在 SOP 保存时自动同步工具绑定关系

**知识与经验的区别**：
- **知识**（RAG 检索的文档）：存储在 `knowledge_bases` 表，通过向量检索获取
- **经验**（SOP 流程定义）：存储在 `skills` 表，通过图结构遍历执行

**追问回答**：
- **口述流程无文档**：通过 `SkillEditor` 的交互式界面，业务专家可以可视化编辑 SOP 图结构，系统自动生成 JSON
- **SOP 修改**：热更新，修改后立即生效，无需重启。版本管理通过 `SkillVersion` 表记录历史版本，支持分支管理（`AgentSkillBranch` 表），类似 Git 的分支模型——每个 Agent 可以有独立的 SOP 分支，修改在分支上进行，审核通过后发布

### Q5：你提到"人工接管"和"反馈进化闭环"，这两个机制具体是怎么工作的？

**期待答题要点：**
- **人工接管：** Agent 执行过程中遇到不确定情况（置信度低、超出能力范围、用户明确要求）时，将任务挂起并通知人工介入，人工决策结果回写到执行上下文，Agent 继续执行
- **反馈进化闭环：** 用户对 Agent 输出给出评价（好评/差评），差评触发技能改写流程——分析失败原因 → 生成修改建议 → 改写 SOP 节点或工具调用策略 → 人工审核后生效
- 能说出反馈数据的存储结构和进化触发的具体条件

**追问（循序渐进）：**
- 人工接管时，Agent 的上下文状态是怎么保存和恢复的？
- 反馈进化是自动改写还是需要人工审核？如何防止自动改写引入回归？
- 有没有具体的指标衡量反馈闭环的效果？比如经过 N 轮反馈后，某 SOP 的成功率提升了多少？

---

**我的回答：**

**人工接管机制**（从 `HumanHandoffService` 代码提取）：

1. **触发条件**：

### Q10：你认为这个项目最大的技术风险是什么？你们是如何应对的？

**我的回答：**

**如果从零开始重新做，我会做以下不同的技术决策：**

1. **数据库选型：SQLite → PostgreSQL**
   - **当前不足**：SQLite 单写者锁导致高并发场景下性能瓶颈，不支持多机分布式部署
   - **改进方案**：直接使用 PostgreSQL，支持并发写入、JSONB 查询、水平扩展
   - **迁移成本**：SQLModel ORM 层无需改动，只需数据迁移脚本

2. **模型分级策略**
   - **当前不足**：默认使用 qwen3.6-27b 模型，所有 LLM 调用使用相同模型配置，成本高
   - **改进方案**：
     - 意图分类：使用 fine-tuned BERT（小模型），延迟低、成本低
     - SOP 执行：使用大模型，保证推理质量
     - 回复生成：根据场景选择模型（简单查询用小模型，复杂推理用大模型）
   - **预期效果**：成本降低 40-50%

3. **SOP 节点内并行工具调用**
   - **当前不足**：单个 SOP 节点内的工具调用是串行的，当一个节点需要调用多个独立工具时延迟较高
   - **改进方案**：支持单个节点内并行调用多个无依赖的工具（如同时查询多个数据源），通过 `asyncio.gather` 并发执行
   - **说明**：任务帧级别已经支持并行调度（`TaskFrameStore` 支持依赖检查 `dependencies_satisfied`），但节点内的工具调用仍是串行的

4. **链路追踪系统**
   - **当前不足**：`AgentEvent` 表数据增长快，查询性能下降
   - **改进方案**：引入专门的 APM 工具（如 Jaeger、Zipkin），支持分布式追踪、数据归档、可视化查询
   - **优势**：专业工具性能更好，支持更复杂的查询和分析

5. **工具调用重试策略**
   - **当前不足**：工具调用失败后由 LLM 决定是否重试，不够智能
   - **改进方案**：
     - 幂等操作（如查询）：自动重试 3 次
     - 非幂等操作（如支付）：不自动重试，需要用户确认
     - 根据错误码判断：5xx 自动重试，4xx 不重试

**工程判断力的成长**：
- 从"能用就行"到"考虑扩展性"：初期选择 SQLite 是为了快速验证，后期意识到需要 PostgreSQL
- 从"单一模型"到"模型分级"：初期所有任务都用大模型，后期意识到需要成本优化
- 从"单任务串行"到"多任务并行调度"：初期只支持单任务执行，后期通过 `TaskFrameStore` 实现任务帧级别的并行调度，支持任务间依赖管理

### Q10：你认为这个项目最大的技术风险是什么？你们是如何应对的？

**我的回答：**

**技术风险 1：LLM 幻觉对 SOP 执行正确性的影响**

- **风险描述**：LLM 可能生成错误的工具调用参数或错误的回复内容，导致 SOP 执行失败
- **应对措施**：
  1. **节点级工具权限控制**：每个 SOP 节点通过 `allowed_actions` 声明可调用的工具，防止越权操作
     ```python
     # _available_tools_for_step() 动态构建可用工具列表
     actions = {action for step in candidate_steps for action in step.get("allowed_actions") or []}
     explicit_names = {action.split(":", 1)[1] for action in actions if action.startswith("call_tool:")}
     allow_any = "call_tool" in actions
     available_tools = [t for t in tools if allow_any or t.name in explicit_names]
     ```
  2. **Agent 级工具可见性控制**：`ToolExecutor` 在执行前检查 Agent 是否有权使用该工具
     ```python
     # ToolExecutor.execute() 中的权限校验
     if agent_id and tool.id not in {row.id for row in visible_tool_rows(db, tenant_id, agent_id)}:
         return self._error(tool.name, "NOT_ALLOWED", "当前员工未启用该工具。")
     ```
  3. **SOP 级工具白名单**：`ToolExecutor` 还检查工具是否在当前 SOP 的允许列表中
     ```python
     if active_skill_id and tool.allowed_skills_json and active_skill_id not in tool.allowed_skills_json:
         return self._error(tool.name, "NOT_ALLOWED", "当前技能不允许调用该工具。")
     ```
  4. **人工接管**：关键节点（如支付、审批）通过 SOP 中的 `handoff` 类型节点强制人工确认

**技术风险 2：工具调用的安全性风险**

- **风险描述**：Agent 可能误操作外部系统（如误删除数据、误发送通知）
- **应对措施**：
  1. **三层工具权限控制**：
     - Agent 级：`visible_tool_rows()` 控制每个 Agent 可见的工具集合
     - SOP 级：`tool.allowed_skills_json` 控制工具在哪些 SOP 中可调用
     - 节点级：`allowed_actions` 控制每个 SOP 节点可调用的具体工具
  2. **工具启用开关**：每个工具有 `enabled` 字段，可随时禁用
  3. **操作确认**：高风险操作（如删除、支付）通过 SOP 中的 `handoff` 节点强制人工确认
  4. **审计日志**：所有工具调用通过 `AgentEvent` 记录，包含调用参数和结果，可追溯
  5. **调用幂等性**：`HarnessInvocationRecord` 确保工具调用幂等，防止重复执行

**技术风险 3：成本风险（LLM 调用费用）**

- **风险描述**：随着用户量和 Agent 数量增长，LLM 调用费用快速增长
- **应对措施**：
  1. **斜杠命令**：确定性操作（如 `/sop`、`/skill`、`/tool`）不调模型，直接路由，减少 LLM 调用
  2. **对话上下文压缩**：`ConversationProjection` 压缩历史消息，减少每次调用的 token 消耗
  3. **异步记忆提取**：`MemoryService.capture_turn()` 异步执行，不阻塞主流程
  4. **模型分级**：系统支持 `ModelConfig` 配置，可为不同场景配置不同模型（待实现智能路由）

**实际效果**：
- 通过斜杠命令和对话上下文压缩，显著降低了 token 消耗
- 未发生因 LLM 幻觉导致的严重事故（通过多层权限控制和人工接管兜底）
