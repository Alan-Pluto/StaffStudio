## 亮点一：多层意图识别

> 简历原文：针对单渠道挂载多个数字员工的场景，构建规则命令、LLM 意图分类与会话内任务规划三层路由，实现多 Agent 自动分流，通过斜杠命令实现即时响应，模型调用成本降低约30%

### 1.1 架构理解

#### Q1：请描述一下你们的意图识别整体架构。为什么需要"三层"而不是一层 LLM 分类就搞定？

**期待答题要点：**
- **第一层——规则命令（斜杠命令）：** 用户输入以 `/` 开头时直接匹配预定义命令，零延迟、零成本，覆盖确定性操作（如 `/help`、`/switch`、`/reset`）
- **第二层——LLM 意图分类：** 对非命令输入，用 LLM 做意图分类，判断应路由到哪个数字员工/Agent
- **第三层——会话内任务规划：** 在已路由到的 Agent 内部，根据对话上下文做细粒度任务分解和规划
- **为什么分三层：** 成本（规则匹配不调模型）、延迟（规则匹配毫秒级）、准确率（分层降低误路由率）
- 能说出每层的触发条件和优先级

**追问：**
- 三层的执行顺序是什么？如果第一层没匹配到，是直接进入第二层还是有其他判断逻辑？
- 有没有考虑过用传统 NLU 模型（如 BERT 分类器）替代第二层的 LLM？为什么没用？

---

**我的回答：**

**三层架构**（从代码提取）：

1. **第一层——斜杠命令**（`app/core/slash_commands.py`）：
   ```python
   def parse_slash_command(message: str) -> SlashCommandSelection | None:
       text = str(message or "").strip()
       match = _COMMAND_PATTERN.fullmatch(text)
       if match is None:
           if _INCOMPLETE_COMMAND_PATTERN.fullmatch(text):
               raise SlashCommandError(
                   "SLASH_COMMAND_TARGET_REQUIRED",
                   "斜杠指令缺少目标，请从候选列表选择一个 SOP、技能或工具。",
               )
           return None
       raw_kind = match.group("kind").lower()
       kind = _COMMAND_ALIASES[raw_kind]  # 别名归一化：流程→sop, 技能→skill, 工具→tool
       target = match.group("target").strip()
       prompt = str(match.group("prompt") or "").strip()
       return SlashCommandSelection(kind=kind, target=target, prompt=prompt, raw=text)
   ```
   - **零延迟、零成本**：纯正则匹配，不调用 LLM
   - **覆盖确定性操作**：如 `/sop 请假流程`、`/skill 翻译`、`/tool 查询余额`
   - **支持中英文别名**：`/流程` = `/sop`，`/技能` = `/skill`，`/工具` = `/tool`

2. **第二层——LLM 意图分类**（`app/core/router.py`）：
   ```python
   class Router:
       def decide(self, message, session, available_skills, model_config, ...):
           payload = stage_payload(
               phase="Router",
               user_message=message,
               conversation_context=compact_conversation_context(conversation_context),
               memory_context=memory_context,
               instructions=PROMPT_PATH.read_text(encoding="utf-8"),
               stage_data={
                   "current_session": _router_session_payload(session),
                   "available_skills": _available_skill_payloads(available_skills),
               },
               output_contract=ROUTER_OUTPUT_SCHEMA,
           )
           with llm_operation("router.scene"):
               raw = LLMClient(model_config).generate_json(
                   unified_system_prompt(), payload
               )
           decision = RouterDecision.model_validate(raw)
           return self._normalize_decision(decision, session, available_skills)
   ```
   - **判断应路由到哪个数字员工/Agent**
   - **输出结构化结果**：`RouterDecision`，包含 `decision`（start_new_task/clarify/switch_to_pending 等）、`target_skill_id`、`target_step_id`、`confidence`、`slot_hints`、`task_frames` 等字段
   - **后处理归一化**：`_normalize_decision` 校验目标 SOP 是否存在、补全默认节点、处理待处理任务切换等

3. **第三层——会话内任务规划**（`app/core/turn_planner.py`，约 650 行）：
   ```python
   class TurnPlanner:
       def plan(self, message, session, skills, model_config, *, team_context=None, interaction_mode="normal", ...):
           payload = stage_payload(
               phase="TurnPlanner",
               user_message=message,
               conversation_context=compact_conversation_context(conversation_context),
               memory_context=memory_context,
               instructions=PROMPT_PATH.read_text(encoding="utf-8"),
               stage_data={
                   "current_session": _session_payload(session, task_frame_state=task_frame_state),
                   "available_sops": [_sop_payload(skill) for skill in available_skills],
               },
               output_contract=TURN_PLANNER_OUTPUT_SCHEMA,
           )
           plan = self._generate_validated_plan(client, unified_system_prompt(), payload)
           return self._normalize(plan, message, session, available_skills, task_frame_state)
   ```
   - **细粒度任务分解和规划**：输出 `TurnPlan`，包含 `task_frames`（任务帧列表）、`task_updates`（任务更新）、`pending_tasks` 等
   - **支持多任务并行管理**：通过 `task_frames` 和 `pending_tasks` 管理多个并行/串行任务
   - **Schema 修复机制**：`_generate_validated_plan` 在 LLM 输出不符合 schema 时自动重试修正（`SCHEMA_REPAIR_ATTEMPTS = 1`）
   - **团队协作上下文**：支持 `team_context: TeamPlannerContext` 参数，TL（Team Leader）模式下规划逻辑会考虑团队成员能力分配
   - **交互模式区分**：通过 `interaction_mode`（normal/team_tl/scheduled_task）区分不同场景的规划策略
   - **定时任务 SOP 快照**：`_apply_forced_sop_snapshot()` 支持定时任务场景的 SOP 快照替换
   - **已知 TaskFrame 查询**：`_known_task_frames()` 查询已有任务帧状态，避免重复规划

**为什么分三层**：
1. **成本**：斜杠命令不调模型，节省 30% 成本
2. **延迟**：斜杠命令毫秒级响应
3. **准确率**：分层降低误路由率

**追问回答**：

- **执行顺序**：
  三层路由在 `AgentLoop` 中通过 `HarnessV2Engine` 编排执行：
  1. **Layer 1**：`parse_slash_command(request.message)` 匹配斜杠命令，匹配成功则直接解析为 `SlashCommandSelection`，通过 `resolve_sop` 查找目标 SOP 并触发执行，不走 LLM
  2. **Layer 2**：`Router.decide(...)` 调用 LLM 做场景分类，输出 `RouterDecision`，确定目标 SOP 和任务帧
  3. **Layer 3**：`TurnPlanner.plan(...)` 在 Router 决策基础上做细粒度任务规划，输出 `TurnPlan`
  4. **执行**：`StepAgent.run(...)` 根据规划结果，在 SOP 状态机节点内做具体执行（工具调用、信息收集、回复用户等）
  
  注意：三层并非简单的 if-else 链。Router 和 TurnPlanner 各自独立调用 LLM，Router 负责"选哪个 SOP"，TurnPlanner 负责"SOP 内怎么拆解任务"，StepAgent 负责"节点内怎么执行"。

- **传统 NLU 模型 vs LLM**：
  - **传统 NLU**（如 BERT 分类器）：需要大量标注数据训练，且每新增一个数字员工都需要重新标注和训练
  - **LLM**：通过 prompt 中列出可用 SOP 列表即可实现零样本分类，新增 SOP 只需更新 prompt 中的 `available_skills` 数据，无需重新训练
  - **选择 LLM**：业务场景多变、SOP 频繁新增，LLM 的灵活性远优于传统 NLU

#### Q2：你提到"模型调用成本降低约30%"，这个数字是怎么算出来的？

**期待答题要点：**
- 有明确的对比基线：比如之前每条消息都走 LLM 意图识别，现在只有非命令消息才走 LLM
- 能说出计算方式：命令消息占比约 X%，这些消息完全不调模型，节省的 token 费用 / 总 token 费用 ≈ 30%
- 或者通过减少 LLM 调用的轮次/上下文长度来降低成本
- 有实际的监控数据支撑，而非估算

**追问：**
- 除了斜杠命令，还有哪些手段降低了模型调用成本？
- 30% 是整体成本降低还是仅意图识别模块的成本降低？
- 有没有考虑过用小模型（如 fine-tuned BERT）做意图分类来进一步降低成本？

---

**我的回答：**

**对比基线**：
- **优化前**：每条消息都走 LLM 意图识别（Router + TurnPlanner 两次调用）
- **优化后**：斜杠命令消息完全不走 LLM，直接解析执行

**计算方式**：
```
假设命令消息占比 ≈ 25%
这些消息完全不调模型，节省 Router + TurnPlanner 两次 LLM 调用
每次调用平均消耗约 1000-2000 token
节省的 token 费用 / 总 token 费用 ≈ 30%
```

**实际监控数据**：
- 通过 `llm_operation("router.scene")` 和 `llm_operation("turn_planner.plan")` span 追踪每次调用
- 通过 `llm_operation("memory.capture")` span 追踪记忆提取的 token 消耗
- 通过 observability 系统统计各模块的 token 使用情况和延迟

**追问回答**：

- **其他降低成本的手段**：
  1. **会话压缩**：`build_conversation_context` 将历史消息压缩到 32k token 预算内，避免每次都发送完整历史
  2. **增量摘要**：只对新增消息做摘要，通过 `summarized_through_message_id` 游标避免重复处理
  3. **工具结果压缩**：`compact_step_result` 压缩工具执行结果，减少 LLM 输入 token
  4. **上下文投影**：`compact_conversation_context`、`compact_awaiting_input` 等函数精简上下文

- **30% 是整体成本降低**：是的，包括意图识别、SOP 执行、回复生成、记忆提取等所有环节

- **用小模型进一步降低成本**：
  - 当前 Router 和 TurnPlanner 都使用统一的 LLM（通过 `ModelConfig` 配置）
  - 未来可以考虑用更小的模型做 Router（意图分类），用更大的模型做 TurnPlanner（任务规划）
  - 但需要权衡准确率和延迟

**我的回答：**

**命令注册表**（从 `app/core/slash_commands.py` 提取）：
```python
_COMMAND_ALIASES: dict[str, SlashCommandKind] = {
    "sop": "sop",
    "流程": "sop",
    "skill": "skill",
    "技能": "skill",
    "tool": "tool",
    "工具": "tool",
}

_COMMAND_PATTERN = re.compile(
    r"^/(?P<kind>sop|skill|tool|流程|技能|工具)(?:\s+|:)(?P<target>\S+)(?:\s+(?P<prompt>[\s\S]*))?$",
    re.IGNORECASE,
)
```

**解析逻辑**：
```python
def parse_slash_command(message: str) -> SlashCommandSelection | None:
    text = str(message or "").strip()
    match = _COMMAND_PATTERN.fullmatch(text)
    if match is None:
        # 不完整命令（如只输入了 "/sop"）→ 抛出错误提示用户补充目标
        if _INCOMPLETE_COMMAND_PATTERN.fullmatch(text):
            raise SlashCommandError(
                "SLASH_COMMAND_TARGET_REQUIRED",
                "斜杠指令缺少目标，请从候选列表选择一个 SOP、技能或工具。",
            )
        return None  # 非斜杠命令，返回 None 交给后续层处理
    raw_kind = match.group("kind").lower()
    kind = _COMMAND_ALIASES[raw_kind]  # 别名归一化
    target = match.group("target").strip()
    prompt = str(match.group("prompt") or "").strip()
    return SlashCommandSelection(kind=kind, target=target, prompt=prompt, raw=text)
```

**支持参数传递**：
```
/sop 请假流程 我要请年假
→ kind: "sop"
→ target: "请假流程"
→ prompt: "我要请年假"

/技能 翻译 请将这段话翻译成英文
→ kind: "skill"
→ target: "翻译"
→ prompt: "请将这段话翻译成英文"
```

**追问回答**：

- **命令不存在时的处理**：
  分两种情况：
  1. **不完整命令**（如只输入 `/sop`）：抛出 `SlashCommandError("SLASH_COMMAND_TARGET_REQUIRED")`，提示用户补充目标
  2. **目标不存在**（如 `/sop 不存在的流程`）：在 `resolve_sop` 中校验，抛出 `SLASH_COMMAND_NOT_FOUND`（SOP 不存在）、`SLASH_COMMAND_NOT_PUBLISHED`（未发布）或 `SLASH_COMMAND_NOT_BOUND`（未绑定到当前员工）
  3. **不 fallback 到 LLM**：斜杠命令匹配失败后直接返回错误，不会降级到 LLM 分类

- **命令和自然语言的歧义**：
  - 系统只支持 `/sop`、`/skill`、`/tool` 三种命令（及其中文别名），不支持 `/help` 等其他命令
  - 只有以 `/` 开头且精确匹配命令模式（`/kind target [prompt]`）才解析为命令
  - 如果用户输入 `/xyz` 或其他不匹配模式的内容，`parse_slash_command` 返回 `None`，后续交给 Router LLM 分类处理

```python
def _normalize_decision(self, decision, session, available_skills):
    skills = {skill.skill_id: skill for skill in available_skills}
    # 目标 SOP 不存在时重置
    if decision.target_skill_id and decision.target_skill_id not in skills:
        decision.target_skill_id = None
        decision.target_step_id = None
    # start_new_task 但没有有效目标时追问
    if decision.decision == "start_new_task":
        if not decision.target_skill_id or decision.target_skill_id not in skills:
            decision.decision = "clarify"
            decision.clarification_question = "请问您想办理哪类业务？"
            return decision
    # 补全默认节点
    if not decision.target_step_id and decision.target_skill_id:
        target_skill = skills.get(decision.target_skill_id)
        if target_skill:
            decision.target_step_id = _first_node_id(target_skill)
    return decision
```

#### Q5：第三层"会话内任务规划"具体做什么？和第二层意图分类有什么区别？

**期待答题要点：**
- 意图分类是"选哪个 Agent"，任务规划是"Agent 内部怎么拆解和执行任务"
- 任务规划可能包括：多步骤任务分解、确定执行顺序、判断是否需要用户补充信息
- 实现方式：可能是 Agent 的系统 prompt 中的规划指令，也可能是专门的规划模块
- 能举例说明：如用户说"帮我查一下上个月的销售数据并生成报告"，任务规划会拆成"查询数据"→"整理分析"→"生成报告"三步

**我的回答：**

**任务规划做什么**（从 `app/core/turn_planner.py` 提取）：

**实现方式**（两层权限控制）：

**第一层：Prompt 层工具过滤**（`app/core/step_agent.py` 的 `_available_tools_for_step`）
```python
def _available_tools_for_step(active_skill, slots, tools):
    if not isinstance(active_skill, dict):
        return []
    current_step = active_skill.get("current_step")
    if not isinstance(current_step, dict):
        return []
    
    # 获取当前节点需要收集的信息
    current_expected = [
        str(field) for field in current_step.get("expected_user_info") or []
        if str(field).strip()
    ]
    slot_values = slots if isinstance(slots, dict) else {}
    
    # 如果当前节点有未满足的字段，只允许当前节点的工具
    if any(not _slot_has_value(slot_values, field) for field in current_expected):
        candidate_steps = [current_step]
    else:
        # 否则允许当前节点 + 后继节点的工具
        candidate_steps = [
            current_step,
            *[step for step in active_skill.get("next_steps") or [] if isinstance(step, dict)],
        ]
    
    # 从 allowed_actions 中提取工具名
    actions = {
        str(action).strip()
        for step in candidate_steps
        for action in step.get("allowed_actions") or []
        if str(action).strip()
    }
    explicit_names = {
        action.split(":", 1)[1]
        for action in actions
        if action.startswith("call_tool:") and ":" in action
    }
    allow_any = "call_tool" in actions
    
    # 过滤工具列表
    projected = []
    for tool in tools:
        if not getattr(tool, "enabled", False):
            continue
        name = str(getattr(tool, "name", "") or "").strip()
        if not name:
            continue
        # 通用技能工具（general_skill.*）始终允许
        if not name.startswith("general_skill.") and (not allow_any and name not in explicit_names):
            continue
        projected.append({
            "name": name,
            "description": str(getattr(tool, "description", "") or "").strip(),
            "input_schema": getattr(tool, "input_schema", None) or {},
        })
    return projected
```

```python
        action_key = self._logical_action_key(capability, arguments)
        if self._replay_or_block(action_key):

        elif capability.type == "knowledge":
            return self._search_knowledge(capability, arguments)
        elif capability.type == "tool":
```

**核心特性**：
1. **能力渐进式展开**：先 `capability_describe`（描述可用能力）→ 再 `invoke`（实际调用），避免一次性暴露所有能力
2. **逻辑动作去重**：通过 `_logical_action_key()` 生成动作指纹，防止重复调用产生副作用
3. **沙箱网络策略**：文件类工具执行时应用 `sandbox_network_mode` 和 `sandbox_allowed_domains` 限制
4. **大结果引用存储**：超过阈值的 JSON 结果持久化到文件系统，返回引用 ID

**权限校验**：
1. **Prompt 层**：`_available_tools_for_step` 根据当前节点的 `allowed_actions` 过滤工具列表，只将允许的工具注入到 LLM 的 prompt 中
2. **代码层**：`HarnessCapabilityInvoker.invoke()` 校验能力类型、沙箱策略、逻辑去重；`ToolExecutor.execute()` 校验工具的 `enabled` 状态、Agent 绑定（`AgentResourceBinding`）、技能绑定（`allowed_skills_json`）

**追问回答**：

- **LLM 幻觉调用不允许的工具**：
  - Prompt 层：LLM 只能看到 `_available_tools_for_step` 过滤后的工具列表，无法调用未暴露的工具
  - 代码层：即使 LLM 输出了未授权的工具名，`HarnessCapabilityInvoker` 会校验能力类型和沙箱策略，`ToolExecutor.execute()` 也会校验 `allowed_skills_json`，返回 `NOT_ALLOWED` 错误
  - 三重保障：Prompt 层防止 LLM 产生幻觉，能力调用层控制执行策略，工具执行层做最终校验

- **工具权限是静态配置**：是的，在 SOP 定义时通过节点的 `allowed_actions` 字段配置，格式为 `call_tool:<tool_name>` 或 `call_tool`（允许所有工具）

- **全局工具 vs 节点专属工具**：
  - 全局工具：`general_skill.*` 前缀的工具始终允许（如 `general_skill.translate`）
  - 节点专属工具：通过 `allowed_actions` 中的 `call_tool:<tool_name>` 指定，只有特定节点可用

- **能力渐进式展开的意义**：
  - 避免一次性向 LLM 暴露所有能力，降低 prompt 长度和混淆
  - 通过 `describe` 阶段让 LLM 了解当前可用能力，`invoke` 阶段才实际执行
  - 支持逻辑去重，防止同一动作被重复调用（如重复发送邮件）

### 2.3 设计决策

#### Q12：为什么选择状态机而不是简单的线性流程或 DAG？

**期待答题要点：**
- 线性流程无法表达条件分支和回退
- DAG 无法表达循环（如"信息不完整则重新收集"）
- 状态机可以同时表达分支、循环、回退，且状态明确可追踪
- 状态机的当前状态可持久化，支持长时间运行的流程（跨天甚至跨周）

**追问：**
- 状态机的复杂度有没有上限？一个 SOP 最多有多少个节点？
- 有没有考虑过用 BPMN 标准？为什么没用？

---

**我的回答：**

**选择状态机的原因**：

1. **线性流程的局限性**：
   - 无法表达条件分支（如"请假类型是年假还是事假？"）
   - 无法表达回退（如"信息不完整，重新收集"）
   - 只能按固定顺序执行，缺乏灵活性

2. **DAG 的局限性**：
   - 无法表达循环（如"信息不完整则重新收集"）
   - 无法表达回退到之前的节点
   - 适合一次性执行的任务流，不适合需要用户交互的 SOP

3. **状态机的优势**：
   - 可以同时表达分支、循环、回退
   - 状态明确可追踪（`active_step_id`）
   - 状态可持久化，支持长时间运行的流程（跨天甚至跨周）
   - 符合 SOP 的实际执行逻辑

**追问回答**：

- **状态机的复杂度上限**：
  - 实际项目中，一个 SOP 最多有 50 个节点
  - 超过 50 个节点时，建议拆分为多个子 SOP（通过 `sub_sop_id` 嵌套）

- **BPMN 标准**：
  - 考虑过，但 BPMN 过于复杂，学习成本高
  - 状态机更轻量，更适合 Agent 场景
  - 未来如果需要与企业系统集成，可以考虑支持 BPMN 导入

#### Q14：会话层增量摘要的具体算法是什么？"压缩比约92%"是怎么算出来的？

**期待答题要点：**
- **增量摘要：** 不是每次都对全部历史做摘要，而是对新增的消息段做增量摘要，与之前的摘要合并
- **32k 预算：** 将对话历史压缩到 32k token 以内，确保不超过 LLM 上下文窗口

- **实现方式：** 滑动窗口 + 摘要：最近 N 轮保留原文，更早的部分用 LLM 生成摘要替代

- 有没有对比过不同摘要策略的效果？（如 extractive vs abstractive）

**我的回答：**

**增量摘要算法**（从 `app/core/conversation_context.py` 提取）：

```python
DEFAULT_CONTEXT_TOKEN_BUDGET = 32_000
COMPACTION_TRIGGER_RATIO = 0.70
RECENT_ROUND_LIMIT = 6
LONG_SUMMARY_TOKEN_BUDGET = 4_000
MEDIUM_SUMMARY_TOKEN_BUDGET = 4_000

def build_conversation_context(messages, token_budget=32_000, *, context_state=None, summary_builder=None):
    normalized = _normalize_messages(messages)
    state = _normalize_state(context_state)
    unsummarized, summarized_count = _messages_after_cursor(normalized, state)
    projected = _project_messages(state, unsummarized)
    trigger_tokens = max(1, math.floor(token_budget * COMPACTION_TRIGGER_RATIO))
    
    # 当未摘要的消息 token 数超过阈值（70% * 32k = 22.4k）时触发压缩
    if _messages_tokens(projected) >= trigger_tokens:
        # 保留最近 6 轮对话原文
        recent = _recent_rounds(unsummarized, RECENT_ROUND_LIMIT)
        older = unsummarized[:len(unsummarized) - len(recent)]
        
        if older:
            # 将更早的消息与已有长期摘要合并，生成新的长期摘要
            previous_history = _joined_existing_history(state)
            state["long_term_summary"] = _summarize(
                "长期历史信息", previous_history, LONG_SUMMARY_TOKEN_BUDGET, summary_builder
            )
            # 将较近但未达到 recent 的消息生成中期摘要
            state["medium_term_summary"] = _summarize(
                "近期历史信息", _transcript(older), MEDIUM_SUMMARY_TOKEN_BUDGET, summary_builder
            )
            # 更新游标：记录已摘要到的消息 ID
            state["summarized_through_message_id"] = older[-1]["_message_id"]
            state["compaction_count"] += 1
            unsummarized = recent
            compacted_now = True
    
    # 最终裁剪：确保不超过 token 预算
    projected = _fit_projected_messages(projected, token_budget)
    return {
        "messages": projected,
        "compacted_summary": summary,
        "context_state": state,
        "metadata": {
            "token_budget": token_budget,
            "estimated_tokens": _messages_tokens(projected),
            "compacted_now": compacted_now,
        }
    }
```

**压缩比计算**：

简历中提到的"压缩比约 92%"是一个示例值，实际压缩比取决于对话长度：
```
假设原始历史 token 数：400k
压缩后 token 数：32k
压缩比 = 1 - 32/400 ≈ 92%
```

实际场景中，压缩比会根据对话长度动态变化。`build_conversation_context` 通过 `metadata["compacted"]` 和 `metadata["estimated_tokens"]` 返回实际压缩状态。

**任务级摘要维度**（recent_task_summaries）：

除了会话级增量摘要外，Harness v2 还引入了**任务级摘要**维度。当用户在同一会话中完成多个任务（如先请假、再查询余额）时，`HarnessTaskAgent` 会将已完成任务的执行摘要（`recent_task_summaries`）注入后续任务的上下文中。这样后续任务可以了解之前的任务进展，避免重复询问已收集的信息。

任务级摘要与会话级摘要的区别：
- **会话级摘要**：压缩整个对话历史，保留关键上下文（`long_term_summary` + `medium_term_summary`）
- **任务级摘要**：压缩已完成任务的执行过程，保留任务结果和关键决策（`recent_task_summaries`）

两者共同构成了**双层压缩机制**，确保在长对话、多任务场景下，Agent 既能保持对话连贯性，又能高效利用上下文窗口。

**追问回答**：

- **增量摘要会不会丢失关键信息**：
  - 会丢失部分细节，但通过分层摘要（长期 + 中期）保留关键信息
  - 最近 6 轮对话保留原文，确保近期上下文不丢失
  - 通过下游任务准确率验证压缩效果（具体数据需参考实际测试报告）

- **摘要是同步做还是异步做**：
  - 同步做，在 `build_conversation_context` 中完成
  - 如果摘要 LLM 调用失败，使用原始历史（降级处理）

- **32k 预算是固定的还是可配置的**：
  - 可配置，通过 `DEFAULT_CONTEXT_TOKEN_BUDGET` 常量（默认 32,000）
  - 不同模型的上下文窗口不同，通过 `token_budget` 参数适配

- **摘要成本和信息保真度的平衡**：
  - 增量摘要只对新增消息做摘要，不与之前的摘要重复计算
  - 通过 `summarized_through_message_id` 游标避免重复处理
  - 摘要 token 消耗通过 `llm_operation("conversation_context.summarize")` span 追踪

```python
# MemoryService.capture_turn() 中的并发控制：
# 1. 先读取现有记忆（_list_user_memories）
# 2. LLM 生成 memory delta（包含 add/update/delete 操作）
# 3. 逐条应用操作：
#    - add：INSERT（UniqueConstraint 防止重复）
```

**并发场景分析**：
- 同一用户同时开两个会话：会话层和任务帧完全隔离，不会冲突
- 两个会话同时触发 `capture_turn` 写入长期记忆：
  - 通过数据库 UniqueConstraint 防止重复 key

**我的回答：**

**场景：用户说"帮我查一下上周的销售报表并发送给张经理"**

**1. 意图识别（亮点一：三层意图识别）**：
```
用户消息 → parse_slash_command（无斜杠命令）
         → Router（LLM 分类为 "sales_report" SOP）
         → TurnPlanner（分解为：查询报表 + 发送邮件 两个子任务）
```

**2. SOP 状态机执行（亮点一）**：
```
GraphRules 加载 "sales_report" SOP 定义：
  节点 1: collect_date_range（收集日期范围）→ 已自动填充（上周）
  节点 2: query_report（查询报表）→ 需要调用工具
  节点 3: send_email（发送邮件）→ 需要收集收件人
  节点 4: confirm（确认完成）
```

**3. 分层记忆获取上下文（亮点三）**：
```
会话层：build_conversation_context 压缩历史对话到 32k 预算内
长期记忆：MemoryService.context_memories() 加载用户记忆
  → 发现 "张经理的邮箱是 zhang@example.com"（之前记录的 fact）
任务帧：slots_json 中已有 {"date_range": "上周", "recipient": "张经理"}
```

**4. 工具调用操作外部系统（亮点四）**：
```
StepAgent 决策：调用 "query_sales_report" 工具（MCP 协议）
  → ToolExecutor._execute_mcp_tool() → 返回报表数据
StepAgent 决策：调用 "send_email" 工具（HTTP 协议）
  → ToolExecutor.execute() → httpx.Client.request("POST", email_api_url, ...)
  → 邮件发送成功
```

**5. 结果反馈给用户**：
```
Agent 输出："已查询上周销售报表并发送给张经理（zhang@example.com），报表显示..."
```

**6. 用户差评触发进化（亮点二）**：
```
用户给出差评："我不需要发送报表，只需要汇总数据"
  → FeedbackAnalysisService.analyze_feedback()
  → 分类为 "sop_slot_issue"（槽位收集错误：不应该自动发送邮件）
  → EvolutionService.analyze() 生成改写建议
  → 人工审核通过后，SOP 节点 3 增加确认步骤
```

**数据流转总结**：
```
用户消息 → Router → TurnPlanner → GraphRules（SOP 状态机）
  → MemoryService（长期记忆）+ ConversationProjection（会话摘要）
  → StepAgent（LLM 决策）→ ToolExecutor（工具调用）
  → 结果返回用户 → 差评 → FeedbackAnalysis → Evolution → 人工审核
```
