# 项目概览与架构

> 本文档深入介绍 Staff Studio 的系统架构、核心模块、数据流和数据库设计，帮助你理解项目的技术实现细节。

---

## 1. 项目定位与目标

### 1.1 项目定位

Staff Studio 是一个**企业级 AI Agent 平台**，专注于构建和管理"数字员工"。与通用对话机器人不同，Staff Studio 的数字员工具有以下特征：

| 特征 | 说明 |
|------|------|
| **有岗位** | 每个数字员工有明确的职位、岗位边界和服务风格 |
| **有能力** | 通过 SOP（标准作业流程）、知识库、工具等定义能力边界 |
| **有记忆** | 支持长期记忆、会话上下文、工作记录 |
| **可协作** | 支持多员工团队协作、真人接管、权限隔离 |
| **可迭代** | 通过反馈、Trace、记忆实现持续进化 |

### 1.2 核心差异化

1. **SOP 驱动执行**：不是简单的对话，而是通过状态机驱动的结构化流程执行复杂任务
2. **多渠道集成**：原生支持微信、企业微信、飞书、钉钉等 IM 渠道
3. **团队协作**：支持多数字员工组队、任务分发、Leader 协调
4. **完整 Trace**：每次执行都有完整的意图识别、检索、技能、工具调用记录

## 2. 系统架构总览

### 2.1 单端口架构

Staff Studio 采用**单端口架构**：一个 FastAPI 进程同时提供 REST API 和 React SPA 静态资源。

```

│  │  /enterprise/*    → 管理后台 SPA                          │  │
│  │  /workspace/*     → 对话工作台 SPA                        │  │

└─────────────────────────────────────────────────────────────────┘
```

**入口文件**：
- `backend/single_port_app.py` → 静态资源挂载、SPA 路由、WebSocket 代理
- `backend/app/main.py` → FastAPI 应用、路由注册、生命周期管理

**状态管理策略**：

Staff Studio 没有使用 Redux 等全局状态管理库，而是采用：
- `useState` / `useRef` → 组件局部状态
- `localStorage` → 持久化用户偏好、当前选择的 Agent
- `CustomEvent` → 跨组件通信（如 Agent 切换通知）

这种设计简化了状态管理，适合中等复杂度的应用。

### 3.2 Agent 管理模块

**核心职责**：管理数字员工的生命周期、能力配置和权限控制。

**关键文件**：
- `backend/app/api/agents.py` → Agent CRUD API
- `backend/app/agents/branching.py` → Agent 能力分支管理

**数据模型**：
```python
# backend/app/db/models.py
class AgentProfile:
    id: str                    # agent_xxxxxxxxxxxxxxxx
    tenant_id: str             # 租户隔离
    name: str                  # 员工姓名
    description: str           # 岗位描述
    persona_prompt: str        # 人设提示词
```

**能力绑定**：
- `AgentResourceBinding` → 绑定知识库、工具、SOP
- `AgentModelBinding` → 绑定模型配置
- `AgentSkillBranch` → SOP 分支（从广场复制后的本地版本）

### 3.3 SOP/技能系统

**核心职责**：定义和执行结构化流程（SOP）。

**SOP 是什么**：
- SOP = Standard Operating Procedure（标准作业流程）
- 用状态机描述的多步骤流程
- 每个步骤有输入槽位、执行动作、输出结果
- 支持条件分支、循环、人工介入

**关键文件**：
- `backend/app/skills/skill_editor.py` → SOP 编辑器
- `backend/app/skills/skill_distiller.py` → 自然语言→SOP 蒸馏
- `backend/app/skills/skill_reflection.py` → SOP 反思优化
- `backend/app/skills/stream_jobs.py` → SOP 流式执行

**SOP 结构示例**：
```json
{
  "skill_id": "skill_xxx",
  "name": "客户投诉处理",
  "steps": [
    {
      "step_id": "step_1",
      "name": "收集信息",
      "slots": ["customer_name", "issue_type", "description"],
      "action": "ask_user"
    },
    {
      "step_id": "step_2",
      "name": "查询订单",
      "slots": ["order_id"],
      "action": "call_tool",
      "tool": "query_order"
    },
    {
      "step_id": "step_3",
      "name": "处理方案",
      "action": "llm_decision",
      "branches": ["refund", "replace", "escalate"]
    }
  ]
}
```

### 3.4 知识库模块

**核心职责**：文档解析、分层索引、智能检索。

**关键特性**：
- **文档结构感知**：保留文档、章节、页面的层级关系
- **分桶索引**：先定位信息可能所在的"桶"，再精确检索
- **来源引用**：检索结果附带原文引用

**关键文件**：
- `backend/app/knowledge/service.py` → 知识库服务
- `backend/app/knowledge/parser.py` → 文档解析
- `backend/app/knowledge/okf.py` → OKF（Open Knowledge Format）处理
- `backend/app/knowledge/citations.py` → 引用格式化

**数据模型层级**：
```
KnowledgeBase (知识库)
├── KnowledgeDocument (文档)
│   ├── KnowledgeBucket (分桶/章节摘要)
│   │   └── KnowledgeChunk (文本块)
│   └── KnowledgeConcept (概念节点)
└── KnowledgeBaseVersion (版本)
```

### 3.5 工具系统

**核心职责**：定义和执行外部工具调用。

**支持的工具类型**：

| 类型 | 说明 | 关键文件 |
|------|------|----------|
| **HTTP** | 调用 REST API | `app/tools/http_request.py` |
| **MCP** | Model Context Protocol 工具 | `app/tools/mcp_client.py` |
| **A2A** | Agent-to-Agent 协议 | `app/tools/a2a_client.py` |
| **Builtin** | 内置工具 | `app/tools/mcp_builtin.py` |

**关键文件**：
- `backend/app/tools/tool_executor.py` → 工具执行引擎
- `backend/app/tools/tool_schema.py` → 工具 Schema 定义

**数据模型**：
```python
class Tool:
    id: str
    tenant_id: str
    name: str
    tool_type: str        # http / mcp / a2a / builtin
    method: str           # GET / POST / ...
    url: str              # 工具端点
    headers_json: dict    # 请求头
    auth_json: dict       # 认证配置
    input_schema: dict    # 输入 Schema
    output_schema: dict   # 输出 Schema

class MCPServer:
    id: str
    tenant_id: str
    name: str
    transport: str        # stdio / streamable_http / sse / builtin
    url: str              # HTTP/SSE 端点
    command: str          # stdio 命令
    discovered_tools_json: list  # 发现的工具列表
```

## 5. 数据库设计

### 5.1 设计原则

1. **多租户隔离**：所有表都有 `tenant_id` 字段
2. **前缀 ID**：`new_id("prefix")` 生成 `{prefix}_{uuid4_hex[:16]}`
3. **JSON 列**：灵活存储扩展字段
4. **Fernet 加密**：敏感凭证加密存储

## 7. 关键设计决策

### 7.1 为什么选择单端口架构？

- **简化部署**：一个进程、一个端口，降低运维复杂度
- **桌面友好**：适合 PyInstaller 打包为单机应用
- **开发便捷**：前后端联调无需跨域配置

### 7.2 为什么使用 SQLite？

- **零配置**：无需安装数据库服务
- **嵌入式**：适合桌面应用和单机部署
- **足够用**：对于中小规模部署性能足够

### 7.3 为什么不用 Redux？

- **复杂度适中**：应用状态管理需求不复杂
- **简化依赖**：减少第三方库依赖
- **原生方案**：`useState` + `CustomEvent` 足够满足需求

### 7.4 为什么 SOP 用状态机？

- **可预测**：状态转移明确，行为可预测
- **可恢复**：中断后可从当前状态恢复
- **可观测**：每个状态转移都可追踪
