# 07 - 知识库模块

## 1. 概述

StaffStudio 的知识库模块是一个**多层级、可溯源、带知识发现**的企业级知识检索系统，核心文件为 `backend/app/knowledge/service.py`（约 2500 行）。

> **注意**：本系统**不使用向量嵌入和向量数据库**，而是采用**关键词评分 + LLM 语义路由**的混合检索方案。这属于广义的"检索增强生成"（Retrieval-Augmented Generation），但检索手段是词法匹配而非向量相似度。

### 核心能力

| 能力 | 说明 |
|------|------|
| 多格式文档摄入 | 支持 PDF、DOCX、MD、TXT、HTML |
| 层级化知识组织 | Document → Bucket（Wiki 页面） → Chunk（引用来源） |
| OKF 知识框架 | 结构化的概念图谱，支持交叉引用 |
| 多路由检索 | 概念路由 → 文档路由 → Bucket 路由 → Chunk 排序 → 证据组装 |
| 引用溯源 | 全链路引用追踪，每条回答都能定位到原始文档段落 |
| 知识发现 | LLM 自动从文档中发现 SOP 和工具建议 |

### 关键文件

```
backend/app/knowledge/
├── service.py      # 核心服务：摄入、检索、发现（~2500 行）
├── parser.py       # 文档解析器：PDF/DOCX/HTML/TXT
├── okf.py          # OKF 知识框架：概念构建、搜索、导出
├── citations.py    # 引用系统：标签压缩、来源归一化
└── schema.py       # Pydantic 数据模型
```

## 2. 文档摄入流水线

### 2.1 十阶段流水线

每次文档上传都会经过一个 **10 阶段的异步流水线**，每个阶段有明确的标签和进度百分比：

```python
INGEST_STAGES = [
    {"key": "queued",         "label": "排队中",           "progress": 0.0},
    {"key": "parsing",        "label": "解析原始资料",      "progress": 0.08},
    {"key": "normalizing",    "label": "规范化 Source",     "progress": 0.16},
    {"key": "documenting",    "label": "写入 Source Document", "progress": 0.24},
    {"key": "bucketing",      "label": "规划 Wiki 页面",    "progress": 0.36},
    {"key": "bucket_writing", "label": "写入 OKF Wiki",    "progress": 0.48},
    {"key": "chunking",       "label": "生成引用来源",      "progress": 0.62},
    {"key": "summarizing",    "label": "刷新 PageIndex",   "progress": 0.74},
    {"key": "discovering",    "label": "发现 SOP/工具",     "progress": 0.88},
    {"key": "done",           "label": "完成入库",          "progress": 1.0},
]
```

### 2.2 摄入入口

```python
@dataclass
class IngestPayload:
    tenant_id: str              # 租户 ID
    knowledge_base_id: str      # 知识库 ID
    filename: str               # 原始文件名
    content_base64: str         # Base64 编码的文件内容
    knowledge_base_version_id: str | None = None
    title: str | None = None
    metadata: dict[str, Any] | None = None
```

### 2.3 各阶段详解

**阶段 1 - Parsing（解析原始资料）**
- 调用 `parser.py` 的 `extract_text()` 函数
- 根据文件扩展名选择解析策略
- 支持格式：`.txt`、`.md`、`.markdown`、`.html`、`.htm`、`.pdf`、`.docx`
- 文本编码自动检测：UTF-8 → UTF-8-sig → GB18030 → Latin-1

**阶段 2 - Normalizing（规范化）**
- 统一换行符（`\r\n` → `\n`）
- 合并连续空行
- 去除首尾空白

**阶段 3 - Documenting（写入 Source Document）**
- 构建章节导航树（`_build_section_nodes()`）
- 生成文档卡片（`_build_document_card()`）：包含标题、摘要、目录大纲、关键实体
- 写入 `KnowledgeDocument` 记录

**阶段 4 - Bucketing（规划 Wiki 页面）**
- 结构分桶：按目录层级自动分组
- LLM 分桶：调用 LLM 按语义和任务用途规划知识主题
- 合并去重，确保每个 Bucket 有唯一 key 和 section 映射

**阶段 5 - Bucket Writing（写入 OKF Wiki）**
- 将 Bucket 规格写入数据库
- 每个 Bucket 包含：标题、摘要、内容（最多 6000 字符）、关联章节 ID

**阶段 6 - Chunking（生成引用来源）**
- 将 Bucket 内容按 `EVIDENCE_CHUNK_CHARS = 900` 字符切分为 Chunk
- 建立关联组（`related_group_id`）：同一连续章节的 Chunk 互相关联
- 记录前后 Chunk 的链接关系

**阶段 7 - Summarizing（刷新 PageIndex）**
- 构建 OKF 概念（`build_okf_for_document()`）
- 写入 `KnowledgeConcept` 记录

**阶段 8 - Discovering（发现 SOP/工具）**
- 调用 LLM 从文档内容中发现可操作的 SOP 和工具
- 通过 `validate_discovered_skill()` 验证技能草稿的合法性
- 写入 `KnowledgeDiscoverySuggestion` 待人工审核

## 3. OKF（Organized Knowledge Framework）

文件：`backend/app/knowledge/okf.py`（~820 行）

OKF 是本系统的**核心创新点**——它把扁平的文档切片组织成**层级化的知识概念图谱**，类似一个自动生成的 Wiki。

### 3.1 核心概念

```
KnowledgeConcept（知识概念）
├── concept_id:     唯一标识，如 "sources/员工手册/入职流程"
├── concept_type:   类型枚举
│   ├── Source Document    源文档
│   ├── Source Section     源文档章节
│   ├── Topic              知识主题
│   ├── Playbook           操作手册
│   ├── Business Rule      业务规则
│   └── Query Analysis     查询分析
├── content_md:     Markdown 内容（含 frontmatter）
├── links_json:     交叉引用链接
├── citations_json: 引用标记
└── source_refs_json: 来源引用
```

### 3.2 概念构建流程

```python
def build_okf_for_document(
    document: KnowledgeDocument,
    section_nodes: list[dict[str, Any]],
    buckets: list[KnowledgeBucket],
) -> list[dict[str, Any]]:
```

为每个文档生成三类概念：
1. **Source Document 概念**：代表整个文档，包含文档卡片信息
2. **Source Section 概念**：每个章节一个概念（最多 80 个）
3. **Bucket 概念**：每个 Bucket 对应一个 Wiki 页面概念

### 3.3 概念搜索

```python
def search_concepts(query: str, concepts: list[KnowledgeConcept], limit: int = 6) -> list[KnowledgeConcept]:
```

搜索策略：
- 对 query 进行分词
- 标题匹配得分：`6.0 + min(len(token), 6)`
- 正文匹配得分：`3.0 + min(len(token), 4) * 0.5`
- 完整查询命中加分：`+10`
- Source Document 类型降权：`-2`（避免粗粒度结果占据前列）
- 最低阈值：`MIN_CONCEPT_SEARCH_SCORE = 4.0`

### 3.4 OKF 导出

支持将知识库导出为 ZIP 包：
- `index.md`：按概念类型分组的目录索引
- `log.md`：更新日志
- `{concept_id}.md`：每个概念的 Markdown 文件

## 4. 搜索流水线

搜索是整个知识库系统最复杂的部分，采用**多路由、逐级收窄**的策略。

### 4.1 整体流程

```
用户查询
  │
  ▼
① 查询降噪 ── 去除 "我想知道"、"请问"、"怎么" 等常见短语
  │
  ▼
② 概念路由 ── 在 OKF 概念中搜索匹配的 Wiki 页面
  │
  ▼
③ 文档路由 ── LLM 从候选文档中选择最相关的（最多 5 篇）
  │            候选上限：SEARCH_DOCUMENT_ROUTE_LIMIT = 120
  │
  ▼
④ Bucket 路由 ── LLM 从候选 Bucket 中选择最相关的
  │               候选上限：SEARCH_BUCKET_ROUTE_LIMIT = 160
  │
  ▼
⑤ Chunk 排序 ── 对选中 Bucket 下的所有 Chunk 进行相关性评分
  │              最低阈值：SEARCH_MIN_CHUNK_SCORE = 2.0
  │
  ▼
⑥ 关联扩展 ── 将命中 Chunk 的同组关联 Chunk 一起展开
  │            RELATED_CHUNK_MAX_COUNT = 6
  │            RELATED_CHUNK_MAX_CHARS = 4800
  │
  ▼
⑦ 证据组装 ── 构建 Evidence Pack，附带引用来源和置信度说明
```

### 4.2 查询降噪

```python
QUERY_NOISE_PHRASES = (
    "我想知道", "麻烦帮我", "什么时候", "告诉我",
    "请问", "怎么", "如何", "什么", "哪些", "哪个", "一下",
)
```

在分词阶段，中文查询会自动去除这些无意义的疑问短语，提取真正的检索关键词。

### 4.3 文档路由（LLM）

```python

        "query": query,
        "max_documents": max_documents,
        "documents": [_document_card_for_route(row) for row in documents],
    }
    raw = LLMClient(model_config).generate_json(
        DOCUMENT_ROUTE_PROMPT.read_text(encoding="utf-8"), payload

    return raw.get("selected_document_ids")
```

- 使用专门的 `knowledge_document_route_prompt.md` 提示词
- 如果 LLM 路由失败，自动降级到词法评分
- 评分权重：标题(3.0) > 文件名(2.0) > 文档卡片(1.0)
- 最低文档分数：`SEARCH_MIN_DOCUMENT_SCORE = 2.0`

### 4.4 Bucket 路由（LLM）

```python

```

- 使用 `knowledge_search_prompt.md` 提示词
- 考虑 `query_type`（answer / policy_check / tool_discovery / skill_discovery）
- Bucket 的 `applicable_query_types` 匹配时加分 +2.0
- 评分权重：标题(3.0) > 摘要(1.8) > 章节路径(1.4) > 内容(0.6)


排序策略：
1. **文本相关性**：章节标题(2.0) + 章节路径(1.5) + 摘要(1.4) + 正文(1.0)
2. **章节加分**：展开章节的得分 × 0.2（上限 3.0）
3. **Bucket 优先级**：高排名 Bucket 的 Chunk 优先
4. **多样性保证**：`_select_diverse_chunk_hits()` 确保每个 Bucket 至少有一个 Chunk 入选

当一个 Chunk 被命中时，它所在连续章节的其他 Chunk 也会一起返回，确保上下文完整：
- 通过 `related_group_id` 识别同组 Chunk
- 通过 `related_chunk_ids` 直接关联
- 窗口大小：最多 6 个 Chunk，总计最多 4800 字符

## 6. 知识发现

### 6.1 发现流程

在文档摄入的最后阶段，系统会调用 LLM 分析文档内容，自动发现：
- **SOP 建议**：可转化为技能图的操作流程
- **工具建议**：可注册为可调用的外部工具
- **警告建议**：需要注意的业务规则

### 6.2 技能验证

```python
def validate_discovered_skill(payload: dict[str, Any]) -> SkillCard:
```

验证规则：
1. **字段校验**：不允许 SkillCard 之外的未知字段
2. **节点完整性**：每个节点必须有 `node_id`、`name`、`instruction`
3. **可达性检查**：从 `start_node_id` 出发必须能到达所有节点
4. **终止性检查**：所有节点必须能到达 `terminal_node_ids`

### 6.3 审核队列

发现结果写入 `KnowledgeDiscoverySuggestion`，状态流转：
- `pending` → `confirmed`（人工确认，创建技能/工具）
- `pending` → `rejected`（人工拒绝）
- `invalid`（验证失败，自动标记）

冲突检测：确认时会检查是否已存在同名的技能或工具。

## 9. 面试高频问题

### Q1：你的知识检索系统和 LangChain 的 RAG 有什么区别？

**答**：最大的区别在于**检索策略**和**知识组织**。LangChain 的默认 RAG 是"文档切片 → 向量检索 → 拼接上下文"，我们的系统有四个关键不同：

1. **多层级路由**：不是直接搜 Chunk，而是先搜概念 → 再选文档 → 再选 Bucket → 最后排 Chunk，逐级收窄，精度更高。
2. **LLM 路由 + 词法降级**：文档和 Bucket 的选择由 LLM 做语义判断，如果 LLM 不可用则自动降级到词法评分，保证可用性。
3. **OKF 知识框架**：不只是扁平的 Chunk，而是将文档组织成 Wiki 式的概念图谱，支持交叉引用。
4. **关联 Chunk 扩展**：命中一个 Chunk 后，自动展开同组关联 Chunk，保证上下文完整性。

### Q2：为什么不用向量数据库做检索？

**答**：这是一个有意识的设计选择。当前系统使用**词法评分 + LLM 路由**的组合方案：
- 词法评分通过加权多字段匹配实现（标题权重 3.0 > 摘要 1.8 > 路径 1.4 > 内容 0.6）
- LLM 路由利用大模型的语义理解能力做文档/Bucket 选择
- 这种方案的优势是**可解释性强**（每个评分步骤都有 trace）、**不依赖外部向量服务**
- 未来可以加入向量检索作为补充路由

### Q3：文档摄入过程中如果失败了怎么办？

**答**：系统有完善的容错机制：
1. **取消支持**：每个阶段都会检查 `_raise_if_ingest_cancelled()`，用户可以随时取消
2. **阶段持久化**：每个阶段的状态和进度都写入数据库，前端可以实时展示
3. **失败清理**：如果摄入失败，文档状态标记为 `failed`，错误信息持久化
4. **取消清理**：取消时会删除已创建的部分数据（Document、Bucket、Chunk、Concept）
5. **内容清理**：完成后清除 Job 中的 `content_base64`，减少存储占用

### Q4：引用系统是如何保证准确性的？

**答**：引用系统通过多层机制保证准确性：
1. **来源归一化**：所有来源（evidence_pack、chunks、concepts、okf_citations）归一化为统一格式
2. **标签压缩**：移除模型幻觉生成的无效引用标记，只保留有实际来源卡片的引用
3. **按出现重编号**：引用按在回答中首次出现的顺序重新编号，用户体验更好
4. **截断恢复**：自动恢复被模型截断的邮箱等关键信息
5. **去重**：基于语义身份（`_normalize_identity`）去重，避免同一来源重复出现

### Q5：知识发现是怎么工作的？

**答**：知识发现是摄入流水线的最后一个阶段：
1. 将文档的 Bucket 信息（标题、摘要、内容摘录）发送给 LLM
2. LLM 分析内容，返回可能存在的 SOP（技能）和工具建议
3. 技能建议会通过 `validate_discovered_skill()` 严格验证：字段合法性、节点完整性、图可达性
4. 验证通过的建议进入审核队列（`pending` 状态），等待人工确认
5. 确认后自动创建对应的 Skill 或 Tool 记录

### Q6：如何处理中文查询的分词问题？

**答**：系统使用了一套针对中文优化的分词策略：
1. 提取连续中文字符（≥2 字）和英文词（≥2 字母）
2. 对中文查询自动去除噪音短语（"我想知道"、"请问"等）
3. 对 ≥3 字的中文词生成 bigram/trigram/4-gram 子词，提高召回率
4. 中文字词权重高于英文词（2.0~2.7 vs 1.2~3.2），因为中文词信息密度更高
5. 最终限制在 96 个检索词以内，避免过度检索

### Q7：Bucket 的规划策略是什么？

**答**：Bucket 规划采用**结构 + LLM 双通道**策略：
1. **结构分桶**：按文档目录的第一层级自动分组，每个顶级章节对应一个 Bucket
2. **LLM 分桶**：将章节信息发给 LLM，让它按语义和任务用途规划知识主题
3. **合并去重**：两个通道的结果按 `bucket_key` 和 `section_ids` 去重
4. **降级兜底**：如果两个通道都没有结果，使用段落分组作为兜底

### Q8：如果要给这个系统加向量检索，你会怎么做？

**答**：可以在现有架构上增量添加：
1. 在 `_search()` 方法中增加一条向量路由，与现有的词法路由并行
2. 在 Chunk 创建时同步写入向量索引（可以在 `_build_chunks()` 后添加钩子）
3. 在 `route_trace` 中增加向量路由的 trace 信息
4. 最终通过一个融合层（如 RRF - Reciprocal Rank Fusion）合并词法和向量的结果
5. 现有的 `KnowledgeSearchResponse` 已经支持扩展，不需要修改 API 契约
