## 2. 常见架构问题

### Q：描述一下你项目的整体架构

**答**：

StaffStudio 是一个 Python 3.11+ FastAPI 后端 + React/TypeScript 前端的企业级 AI Agent 平台，架构分为六层：

```
┌─────────────────────────────────────────────────────┐
│  渠道层（Channels）                                   │
│  飞书 / 钉钉 / 企业微信 / Web / API                   │
├─────────────────────────────────────────────────────┤
│  会话层（Session）                                     │
│  会话管理 / 消息路由 / 收件箱                             │
├─────────────────────────────────────────────────────┤
│  Agent 引擎层（Harness v2）                           │
│  意图路由 → 轮次规划 → 步骤执行 → 反思 → 回复生成        │
├─────────────────────────────────────────────────────┤
│  能力层                                               │
│  技能系统 / 工具调用 / 知识库检索 / 记忆 / 团队协作       │
├─────────────────────────────────────────────────────┤
│  LLM 集成层                                          │
│  多协议驱动 / Stage 协议 / 提示词管理 / 可观测性          │
├─────────────────────────────────────────────────────┤
│  基础设施层                                           │
│  SQLite / 加密 / 可观测性 / 异步任务                     │
└─────────────────────────────────────────────────────┘
```

数据流：用户消息 → 渠道适配器 → 消息路由 → 会话绑定 → Harness 引擎 → LLM 调用 → 回复 → 渠道发送。

### Q：你的 Agent 系统是怎么工作的？

**答**：

Agent 的核心是 Harness v2 引擎，每轮对话经过五个阶段：

1. **Router（路由器）**：判断用户意图——是继续当前任务、切换任务、还是新建任务。输出决策和任务帧。
2. **Turn Planner（轮次规划器）**：决定本轮要执行什么——继续 SOP 步骤、发起新任务、还是纯对话回复。支持多任务并行和任务依赖。
3. **Step Agent（步骤执行器）**：执行当前步骤的具体动作——回复用户、调用工具、查询知识库、推进到下一步、或请求人工介入。
4. **Reflection（反思器）**：检查步骤执行结果——工具调用是否成功、回复是否准确、是否需要重试或换工具。
5. **Response Generator（回复生成器）**：将最终结果组织为自然语言回复，注入知识库引用和格式化内容。

每个阶段都有独立的提示词模板和输出 Schema，通过 Stage Protocol 标准化管理。

### Q：你的系统和一个简单的 ChatBot 有什么区别？

**答**：

核心区别在三个方面：

1. **任务编排 vs 单轮问答**：ChatBot 是"一问一答"，我们的系统支持多步骤 SOP 任务。比如"帮我发起报销"，Agent 会按技能图的节点逐步执行：收集发票信息 → 校验金额 → 填写表单 → 提交审批，每步都可以调用不同工具。

2. **多 Agent 协作 vs 单一模型**：我们的系统支持团队协作——一个任务可以由主 Agent 执行，也可以分配给团队中的其他 Agent。Turn Planner 的 `execution_target` 字段决定是"自己执行"还是"分配给同事"。

3. **知识驱动 vs 纯模型能力**：ChatBot 只依赖模型训练数据，我们的系统有完整的知识检索模块，Agent 可以在执行过程中主动查询企业知识库，获取最新的政策、流程和数据结构。

### Q：你是如何处理并发请求的？

**答**：

1. **异步任务队列**：文档摄入等耗时操作通过 `KnowledgeIngestJob` 异步执行，不阻塞主线程
2. **独立数据库 Session**：每个异步任务创建独立的 `Session(engine)`，避免连接冲突
3. **取消令牌**：LLM 流式调用支持 `CancellationToken`，用户取消时可以立即中断
4. **SQLModel ORM**：数据库操作通过 ORM 管理，连接池自动处理并发

### Q：你是如何保证数据一致性的？

**答**：

1. **事务管理**：关键操作使用 `db.commit()` / `db.rollback()` 保证原子性
2. **乐观并发控制**：模型配置通过 `config_revision` 和 `security_revision` 检测并发修改
3. **幂等设计**：摄入任务通过 `job_id` 保证幂等，重复执行不会产生重复数据
4. **状态机**：摄入任务有明确的状态流转（queued → running → succeeded/failed/cancelled），防止状态跳跃
5. **冲突检测**：知识发现确认时检查唯一约束，`IntegrityError` 捕获并发冲突

## 3. 模块深度问题

### 3.1 意图识别

**Q：你的系统是怎么理解用户意图的？**

**答**：

意图识别由 Router 阶段完成，核心流程：

1. 将用户消息、对话上下文、记忆上下文、可用技能列表组装为 Stage Payload
2. 使用 `router_prompt.md` 提示词让 LLM 分析意图
3. LLM 输出结构化 JSON，包含 `decision`（决策类型）、`confidence`（置信度）、`user_intent`（意图描述）
4. 决策类型包括：`continue_active`（继续当前任务）、`switch_to_pending`（切换到待处理任务）、`create_pending`（创建新待处理任务）、`answer_only`（纯对话回复）、`clarify`（需要澄清）

关键设计是**置信度驱动**——如果 `confidence` 低于阈值，系统会主动发起澄清而不是猜测。

**Q：意图模糊时怎么处理？**

**答**：

三种策略：
1. **主动澄清**：Router 输出 `decision: "clarify"` 和 `clarification_question`，系统向用户追问
2. **多任务帧**：如果用户消息涉及多个任务，Router 可以输出多个 `task_frames`，每个帧独立处理
3. **待处理队列**：不确定的任务放入 `pending_tasks`，等后续消息明确后再激活

---

### 3.2 任务编排

**Q：你是如何编排复杂的多步骤任务的？**

**答**：

任务编排基于**技能图（Skill Graph）**模型：

```python
SkillCard:
  skill_id: "expense_report"
  start_node_id: "collect_info"
  terminal_node_ids: ["submit"]
  nodes: [
    {node_id: "collect_info", name: "收集信息", instruction: "..."},
    {node_id: "validate", name: "校验数据", instruction: "..."},
    {node_id: "submit", name: "提交审批", instruction: "..."},
  ]
  edges: [
    {source_node_id: "collect_info", next_node_id: "validate"},
    {source_node_id: "validate", next_node_id: "submit"},
  ]
```

Step Agent 根据当前节点执行操作，通过 `action: "advance"` 推进到下一个节点。每个节点可以：
- `reply`：回复用户
- `call_tool`：调用外部工具
- `query_knowledge`：查询知识库
- `ask_user`：等待用户输入
- `handoff`：转交人工

**Q：步骤失败了怎么办？**

**答**：

Reflection 阶段负责错误处理：
1. **重试当前工具**：`action: "retry_tool"`，比如网络超时后重试
2. **换另一个工具**：`action: "try_other_tool"`，比如一个 API 不可用就换备用
3. **修改步骤**：`action: "revise_step"`，调整参数后重试
4. **请求用户帮助**：`action: "ask_user"`，比如需要用户确认替代方案
5. **停止执行**：`action: "stop"`，无法继续时优雅终止

**Q：崩溃恢复是怎么做的？**

**答**：

1. 每个任务的当前节点、已收集的 slot 数据都持久化在数据库中
2. 会话恢复时，Harness 从持久化状态重建执行上下文
3. 技能图的节点是幂等的——同一个节点可以安全地重新执行
4. `execution_context.py` 管理执行状态的序列化和反序列化

### 3.3 多 Agent 协作

**Q：多个 Agent 是怎么协同工作的？**

**答**：

Turn Planner 支持**任务分配**：

```python
task_frame = {
    "kind": "sop",
    "execution_target": "team_member",    # 分配给团队成员
    "assignee_agent_id": "agent_finance", # 指定 Agent
    "activation_condition": {},           # 激活条件
}
```

协作模式：
1. **主从模式**：主 Agent 拆解任务，分配给专业 Agent（如财务 Agent、HR Agent）
2. **并行执行**：多个独立任务可以同时分配给不同 Agent
3. **依赖管理**：`depends_on_task_ids` 定义任务依赖，前置任务完成后才激活后续任务

**Q：如何防止任务冲突？**

**答**：

1. **单活跃任务**：同一时间只有一个 `active` 任务在执行
2. **待处理队列**：新任务进入 `pending` 队列，按优先级排序
3. **Router 仲裁**：当用户消息可能影响多个任务时，Router 决定优先级
4. **状态隔离**：每个任务有独立的 slot 数据和执行上下文

### 3.4 记忆系统

**Q：你的 Agent 是怎么记住东西的？**

**答**：

记忆系统分三层：

1. **短期记忆（对话上下文）**：当前会话的消息历史，通过 `conversation_context` 传递给每个阶段
2. **长期记忆（Memory Service）**：`memory/service.py` 管理持久化记忆，`memory_extractor_prompt.md` 提示词让 LLM 从对话中提取值得记住的信息
3. **知识记忆（Knowledge Base）**：企业知识库作为外部记忆，Agent 可以通过 `query_knowledge` 动作主动检索

记忆注入方式：Stage Protocol 的 `memory_context` 字段将相关记忆注入到 Router 和 Turn Planner 的输入中。

**Q：如何防止记忆爆炸？**

**答**：

1. **选择性提取**：不是所有对话都存入长期记忆，只有 LLM 判断有价值的信息才会提取
2. **去重**：记忆提取时检查是否已存在相似内容
3. **上下文窗口控制**：注入 Stage 的记忆条数有限制，只注入最相关的
4. **记忆衰减**：旧的记忆优先级降低，新的记忆优先注入

### 3.5 工具调用

**Q：你的 Agent 是怎么调用外部工具的？**

**答**：

工具调用支持三种协议：

1. **HTTP 工具**：`tools/http_request.py` — 直接发起 HTTP 请求，支持自定义 method、headers、auth
2. **MCP 工具**：`tools/mcp_client.py` — 通过 Model Context Protocol 调用 MCP 服务器
3. **A2A 工具**：`tools/a2a_client.py` — Agent-to-Agent 协议，调用其他 Agent 的能力

Step Agent 通过 `action: "call_tool"` 触发工具调用，输出 `tool_call: {name, arguments}`。`tool_executor.py` 负责实际执行和结果回传。

**Q：支持哪些工具协议？**

**答**：

| 协议 | 文件 | 说明 |
|------|------|------|
| HTTP REST | `http_request.py` | 标准 HTTP 请求，支持 GET/POST/PUT/DELETE |
| MCP | `mcp_client.py` + `mcp_builtin.py` | Model Context Protocol，标准化工具接入 |
| A2A | `a2a_client.py` + `a2a_recovery.py` | Agent-to-Agent，支持跨 Agent 调用和故障恢复 |

### 3.6 知识库模块

**Q：你的知识检索是怎么工作的？**

**答**：

四级路由检索流水线：

1. **概念路由**：在 OKF 概念图谱中搜索匹配的 Wiki 页面
2. **文档路由**：LLM 从候选文档中选择最相关的（最多 5 篇），失败时降级到词法评分
3. **Bucket 路由**：LLM 从候选 Bucket 中选择最相关的知识主题
4. **Chunk 排序**：对选中 Bucket 下的 Chunk 进行加权评分 + 多样性选择 + 关联扩展

最终组装 Evidence Pack，每条证据带有来源路径和置信度说明。

**Q：你的知识检索和常见的向量 RAG 有什么区别？**

**答**：

三个关键差异：

1. **不是纯向量检索**：我们使用"LLM 路由 + 词法评分"的组合，优势是可解释（每步都有 trace）且不依赖外部向量服务
2. **层级化知识组织**：Document → Bucket → Chunk 三层结构，比扁平切片更精准
3. **关联 Chunk 扩展**：命中一个 Chunk 后自动展开同组关联 Chunk，保证上下文完整性，而不是只返回孤立的片段

## 4. 系统设计问题

### Q：如果要把这个系统扩展到高并发，你会怎么做？

**答**：

1. **LLM 调用层**：
   - 添加请求队列和速率限制，避免打满模型 API
   - 实现模型负载均衡，多个 API Key / 多个 provider 轮转
   - 缓存常见查询的 LLM 响应（如路由决策）

2. **知识库层**：
   - 引入向量数据库（如 Milvus / Qdrant）加速检索
   - 文档摄入使用消息队列（如 Redis Stream）解耦
   - 热门知识库的搜索结果缓存

3. **会话层**：
   - 会话状态存入 Redis，支持多实例部署
   - WebSocket 连接通过 sticky session 或 pub/sub 管理

4. **数据层**：
   - SQLite → PostgreSQL 迁移
   - 读写分离，搜索走只读副本

### Q：如何添加一个新的渠道（比如 Slack）？

**答**：

参考现有的渠道适配器模式：

1. 在 `channels/adapters/` 下创建 `slack_adapter.py`
2. 实现消息接收：Slack Event → 统一消息格式
3. 实现消息发送：统一回复格式 → Slack API
4. 在 `channels/service_routing.py` 中注册路由规则
5. 处理渠道特有功能：线程回复、表情反应、文件上传等

关键设计是**渠道无关的消息格式**——核心系统只处理统一格式的消息，渠道适配器负责双向转换。

### Q：如何提高意图识别的准确率？

**答**：

1. **Few-shot 示例**：在 Router 提示词中加入典型意图的示例
2. **技能描述优化**：Router 依赖技能描述来匹配意图，描述越精确，路由越准确
3. **置信度阈值调优**：低置信度时主动澄清，避免误判
4. **上下文增强**：注入更多对话历史和用户画像，帮助 LLM 理解上下文
5. **反馈闭环**：记录路由决策和用户后续行为，用于分析和优化提示词

## 5. 行为/经验类问题

### Q：你做过的最有挑战的技术问题是什么？

**建议回答方向**（选择你实际参与的部分）：

**知识检索方向**：
> 最有挑战的是设计知识库的多路由检索流水线。难点在于：既要保证检索精度（不能返回无关内容），又要保证召回率（不能遗漏关键信息），还要可解释（用户问"为什么引用这条"时能说清楚）。最终我设计了一套四级路由 + trace 记录的方案，每个阶段的选择理由都记录在 `route_trace` 中。

**LLM 集成方向**：
> 最有挑战的是 JSON 修复机制。不同模型输出 JSON 的可靠性差异很大，有些模型会输出 Markdown 包裹的 JSON，有些会在 JSON 后面加解释文字。我设计了三层容错：先用 `response_format` 约束，失败后将错误信息注入下一轮让模型自我修正，最后还支持 JSON Sequence 解析。这套机制把 JSON 解析成功率从约 85% 提升到了 99% 以上。

**架构方向**：
> 最有挑战的是 Stage Protocol 的设计。Agent 系统有 5 个处理阶段，每个阶段需要不同的提示词和输出格式。最初每个阶段各自管理输入输出，导致提示词不一致、输出格式错误频发。我抽象出了 Stage Protocol，统一了输入结构（`stage_payload`）和输出约束（`output_contract`），让所有阶段共享同一套契约。

### Q：你是怎么设计 Harness v2 引擎的？

**答**：

Harness v2 的设计遵循三个原则：

1. **图执行模型**：每个技能是一个有向图（Skill Graph），节点是步骤，边是流转关系。这比线性 pipeline 灵活——支持条件分支、循环、并行。

2. **阶段分离**：一轮对话的五个阶段（Router → Planner → StepAgent → Reflection → ResponseGenerator）各自独立，通过 Stage Protocol 传递数据。每个阶段可以独立优化提示词而不影响其他阶段。

3. **可恢复执行**：执行上下文（当前节点、已收集的 slot、工具调用结果）持久化在数据库中。即使进程重启，也能从上次中断的地方继续。

### Q：如果能重新来过，你会做什么不同的选择？

**建议回答方向**：

> 1. **向量检索**：最初为了简化部署选择了纯词法检索，但如果重新设计，我会在第一天就引入向量检索作为补充路由，用 RRF（Reciprocal Rank Fusion）融合结果。
>
> 2. **提示词版本管理**：提示词目前是 Markdown 文件，修改后没有版本追踪。如果能重来，我会把提示词纳入版本管理，支持 A/B 测试。
>
> 3. **测试覆盖**：LLM 调用的集成测试比较难写（因为输出不确定），如果能重来，我会在早期就建立基于 fixture 的 mock 测试框架。

## 6. 项目展示技巧

### 6.1 如何自信地介绍项目

1. **先说定位**：一句话说明项目是什么——"这是一个企业级 AI Agent 平台"
2. **再说亮点**：挑 2-3 个最有技术含量的模块深入讲
3. **用数字说话**：代码行数（service.py 2500 行、client.py 1900 行）、支持协议数（4 种）、检索阶段数（4 级）
4. **展示架构图**：如果面试允许白板/纸笔，画出六层架构图

### 6.3 如何回答你没实现的部分

**原则：诚实 + 展示理解**

> "这部分不是我直接实现的，但我了解它的设计。比如飞书渠道的接入，它通过 `feishu_runtime.py` 处理事件回调，消息经过 `service_intake.py` 统一入口后路由到对应的会话。我主要做的是知识库模块，但整个消息流转的架构我是清楚的。"

**切忌**：
- 不要假装是自己做的
- 不要说"这个我不清楚"就结束
- 展示你对整体架构的理解，即使具体实现不是你做的

### 6.4 常见追问应对

**Q：这个和 LangChain 有什么区别？**

> LangChain 是一个通用框架，我们的是针对企业场景的深度定制。核心区别：(1) 我们的知识检索不是简单的切片+向量检索，而是"关键词评分 + LLM 路由"的四级方案；(2) 我们的 LLM 集成层支持 4 种协议的统一抽象，LangChain 对 Responses API 的支持不够灵活；(3) 我们有完整的技能图执行引擎，LangChain 的 Agent 模型相对简单。

**Q：为什么选 FastAPI 而不是 Django/Flask？**

> FastAPI 的异步支持最好，LLM 调用天然是 IO 密集型，异步可以显著提高并发能力。另外 FastAPI 的 Pydantic 集成让数据验证非常方便，我们的数据模型大量使用 Pydantic。

**Q：为什么用 SQLite 而不是 PostgreSQL？**

> 当前阶段的目标是简化部署——桌面版和单机部署不需要额外的数据库服务。SQLModel ORM 让我们可以无痛迁移到 PostgreSQL，只需要改连接字符串。

**Q：你的系统支持多少并发用户？**

> 单实例可以支撑约 50-100 个并发会话（主要瓶颈是 LLM API 调用延迟）。通过水平扩展（多实例 + Redis 会话存储）可以线性扩展。知识库检索本身很快（毫秒级），瓶颈在 LLM 路由阶段。
