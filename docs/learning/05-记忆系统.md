# 第五章：记忆系统（Memory System）

> **核心文件**：`backend/app/memory/service.py`、`backend/app/memory/jobs.py`
>
> **学习目标**：理解 AI Agent 如何实现"跨对话的长期记忆"，让每个数字员工都能记住用户的偏好、身份和背景，从而提供个性化服务。

---

## 1. 概述

### 1.1 为什么需要记忆系统？

在客服、销售等场景中，用户每次对话都可能涉及不同的会话（session）。如果 Agent 每次对话都"失忆"，用户体验会非常差。记忆系统解决的核心问题是：

- **跨会话持久化**：用户上次说过"我喜欢用邮件沟通"，下次对话时 Agent 应该知道。
- **个性化行为**：不同用户有不同的偏好，Agent 需要根据记忆调整回复风格。
- **多 Agent 隔离**：同一个用户可能和多个数字员工交互，每个 Agent 需要独立的记忆空间。

### 1.2 三种记忆类型

系统定义了三种合法的记忆类型（`ALLOWED_MEMORY_KINDS`）：

| 类型 | 含义 | 示例 | 典型 importance |
|------|------|------|----------------|
| `profile` | 用户身份信息 | 称呼"王总"、姓名 | 0.9+ |
| `preference` | 稳定偏好 | "喜欢邮件沟通"、"偏好产品 A3" | 0.75-0.9 |
| `fact` | 长期背景事实 | "用户是 VIP 客户"、"公司有 500 人" | 0.5-0.7 |

> **注意**：系统**不会**把业务流水（"用户刚查了订单 #12345"）存入长期记忆。这些由会话上下文和 session slots 管理。

### 1.3 架构全景

```
用户消息 ──► Harness Agent Loop ──► 生成回复
                                       │
                                       ▼
                              异步任务入队 (jobs.py)
                                       │
                                       ▼
                              MemoryService.capture_turn()
                                       │
                        ┌──────────────┼──────────────┐
                        ▼              ▼              ▼
                  加载已有记忆    LLM 抽取新记忆   归一化 & 去重
                        │              │              │
                        └──────────────┼──────────────┘
                                       ▼
                                  持久化到 DB
                                       │
                        ┌──────────────┴──────────────┐
                        ▼                              ▼
                 下一轮对话注入                  API 查询展示
                (memory_context)               (recall / context_memories)
```

### 2.2 Agent 作用域隔离

记忆通过 `metadata_json.agent_id` 实现 Agent 级别的隔离。关键逻辑：

```python
# backend/app/memory/service.py
def memory_matches_agent(record: MemoryRecord, agent_id: str | None) -> bool:
    """判断一条记忆是否属于指定 Agent。"""
    if not agent_id:
        return True  # 不指定 Agent 时返回所有记忆
    return memory_agent_id(record) == agent_id

def memory_agent_id(record: MemoryRecord) -> str | None:
    """从 metadata 中提取 agent_id。"""
    metadata = record.metadata_json or {}
    value = metadata.get("agent_id")
    if isinstance(value, str) and value.strip():
        return value.strip()
    return None
```

**回退匹配**：如果记忆没有显式的 `agent_id`，系统会检查该记忆关联的 `session_id` 对应的 `ChatSession.agent_id`：

```python
def _memory_matches_agent(self, record: MemoryRecord, agent_id: str | None) -> bool:
    if memory_matches_agent(record, agent_id):
        return True
    # 回退：通过 session 关联推断
    if not agent_id or memory_agent_id(record) or not record.session_id:
        return False
    session = self.db.get(ChatSession, record.session_id)
    return bool(session and session.agent_id == agent_id)
```

### 3.3 读取去重

同一个 key 可能因为并发写入产生多条记录。`memory_rows_for_read()` 保证读取时只返回一条：

```python
def memory_rows_for_read(rows: list[MemoryRecord]) -> list[MemoryRecord]:
    visible: list[MemoryRecord] = []
    seen_keys: set[tuple[str, str, str | None, str]] = set()
    for row in rows:
        dedupe_key = (row.user_id, row.kind, memory_agent_id(row), _read_dedupe_key(row))
        if dedupe_key in seen_keys:
            continue
        seen_keys.add(dedupe_key)
        visible.append(row)
    return visible
```

去重键由四部分组成：`(user_id, kind, agent_id, key)`，确保同一用户在同一 Agent 下、同一种类的同一 key 只出现一次。

### 4.4 更新归一化

`_normalize_memory_updates()` 对 LLM 输出做严格校验：

```python
def _normalize_memory_updates(raw: dict[str, Any]) -> list[dict[str, Any]]:
    items = raw.get("memories")
    if not isinstance(items, list):
        return []

    updates = []
    for item in items:
        kind = str(item.get("kind") or "").strip()
        if kind not in ALLOWED_MEMORY_KINDS:  # 只接受 profile/preference/fact
            continue
        content = str(item.get("content") or "").strip()
        operation = str(item.get("operation") or "upsert").strip().lower()
        if operation not in {"upsert", "delete"}:
            operation = "upsert"
        if operation == "upsert" and not content:
            continue  # upsert 必须有内容
        key = _normalize_memory_key(item.get("key"), kind, content)
        updates.append({
            "operation": operation,
            "kind": kind,
            "key": key,
            "content": content,
            "importance": _normalize_importance(item.get("importance")),
            "reason": str(item.get("reason") or "").strip()[:300],
        })
    return updates
```

## 5. 记忆 Key 管理

### 5.1 Key 归一化

每条记忆都有一个稳定的 key，用于去重和更新：

```python
def _normalize_memory_key(value: Any, kind: str, content: str) -> str:
    # 优先使用 LLM 提供的 key，做正则归一化
    if isinstance(value, str):
        normalized = re.sub(r"[^a-zA-Z0-9_]+", "_", value.strip().lower()).strip("_")
        if normalized:
            return normalized[:80]
    # 回退：用 kind + content 的 MD5 摘要
    digest = hashlib.md5(f"{kind}:{content}".encode("utf-8"), usedforsecurity=False).hexdigest()[:12]
    return f"{kind}_{digest}"
```

归一化规则：
- 转小写
- 非字母数字字符替换为 `_`
- 去除首尾 `_`
- 最长 80 字符
- 回退方案：`MD5("kind:content")[:12]`

### 5.2 Upsert 逻辑

```python
def _upsert_keyed_memory(self, tenant_id, user_id, username, session_id, kind, key, content, importance, metadata, agent_id):
    existing, duplicates = self._find_keyed_memory_candidates(tenant_id, user_id, kind, key, agent_id=agent_id)

    if existing:
        # 更新已有记录
        existing.content = content[:1200]       # 截断保护
        existing.username = username
        existing.session_id = session_id
        existing.importance = importance
        existing.updated_at = now
        existing.metadata_json = {**(existing.metadata_json or {}), **metadata}
        record = existing
    else:
        # 创建新记录
        record = MemoryRecord(
            tenant_id=tenant_id, user_id=user_id, username=username,
            session_id=session_id, kind=kind, content=content[:1200],
            importance=importance, metadata_json=metadata,
        )
        self.db.add(record)

    # 清理重复项
    for duplicate in duplicates:
        if duplicate.id != record.id:
            self.db.delete(duplicate)
    return record
```

### 5.3 查找候选记录

```python
def _find_keyed_memory_candidates(self, tenant_id, user_id, kind, key, agent_id=None):
    rows = list(
        self.db.exec(
            select(MemoryRecord)
            .where(
                MemoryRecord.tenant_id == tenant_id,
                MemoryRecord.user_id == user_id,
                MemoryRecord.kind == kind,
            )
            .order_by(MemoryRecord.updated_at.desc())
        ).all()
    )
    if agent_id:
        rows = [row for row in rows if self._memory_matches_agent(row, agent_id)]
    candidates = [row for row in rows if _memory_matches_key(row, key)]
    if not candidates:
        return None, []
    return candidates[0], candidates[1:]  # 第一条保留，其余为重复
```

### 6.1 完整时序

### 6.2 记忆注入

在 TurnPlanner 构建上下文时，`context_memories()` 的结果被注入为 `memory_context`，让 LLM 在生成回复时能看到用户的历史记忆。

### 6.3 Slot 水合

记忆值还可以填充 SOP 流程中的 slot。例如，如果记忆中存储了用户的称呼"王总"，SOP 流程中需要"客户称呼"这个 slot 时，可以直接从记忆中取值。

### 6.4 对话消息收集

后台任务会收集当前轮次的完整对话历史（最多 12 条消息），作为 LLM 抽取记忆的输入：

## 7. 设计决策

### 7.1 为什么用 LLM 抽取而不是关键词匹配？

| 方案 | 优点 | 缺点 |
|------|------|------|
| 关键词/正则 | 速度快、成本低 | 无法理解上下文，误抽取率高 |
| LLM 抽取 | 理解语义，准确区分"业务流水"和"长期记忆" | 有 LLM 调用成本 |

系统选择了 LLM 抽取，因为记忆质量远比成本重要。一条错误的记忆（比如把订单号存为偏好）会严重影响用户体验。

### 7.2 为什么用 Key 去重？

如果不做去重，每次用户说"我喜欢邮件沟通"都会新增一条记忆，导致记忆膨胀。Key 机制保证：
- 同一 key 只保留最新版本
- 更新操作（"我现在喜欢电话沟通"）会覆盖旧值
- 读取时自动去重，即使写入时产生了重复

### 7.3 为什么需要 Agent 作用域隔离？

同一个用户可能和"销售 Agent"、"售后 Agent"分别交互。不同 Agent 需要不同的上下文：
- 销售 Agent 记住用户的产品偏好
- 售后 Agent 记住用户的服务约束

如果不隔离，Agent 可能会混淆不同场景的上下文。

### 7.4 内容截断保护

```python
content[:1200]  # 普通记忆最长 1200 字符
summary[:1800]  # 摘要最长 1800 字符
```

防止 LLM 生成过长的记忆内容，控制存储成本和注入上下文时 token 消耗。

### 7.5 异步执行

记忆捕获通过 `enqueue_async_job()` 异步执行，好处是：
- 不阻塞用户请求的响应
- 即使记忆抽取失败，也不影响主流程
- 失败会被记录为 `memory_error` 事件，便于排查

## 8. 面试准备题

### Q1：记忆系统如何防止"记忆膨胀"？

**答题要点**：
1. Key 归一化：`re.sub(r"[^a-zA-Z0-9_]+", "_", value.strip().lower())`，相同语义的 key 归一化为同一字符串
2. Upsert 语义：相同 key 的写入是更新而非新增
3. 读取去重：`memory_rows_for_read()` 按 `(user_id, kind, agent_id, key)` 去重
4. 写入时清理：`_find_keyed_memory_candidates()` 找到重复项后自动删除多余的
5. 内容截断：1200 字符上限

### Q2：如何保证记忆不会跨 Agent 泄露？

**答题要点**：
1. 写入时：`metadata.agent_id` 记录记忆归属的 Agent
2. 读取时：`_memory_matches_agent()` 先检查显式 `agent_id`，再回退到 `session.agent_id`
3. 查询过滤：`_list_user_memories()` 在数据库查询后做 Agent 级别的过滤

### Q3：为什么记忆捕获要异步执行？如果失败了怎么办？

**答题要点**：
1. 异步不阻塞主流程：用户不需要等记忆抽取完成才收到回复
2. 失败隔离：`jobs.py` 中用 `try/except` 包裹，失败只记录 `memory_error` 事件
3. 幂等性：即使重试也不会产生重复记忆（Key 去重保证）

### Q4：LLM 抽取 Prompt 如何防止把业务流水存为长期记忆？

**答题要点**：
1. Prompt 中明确禁止："不要保存'用户本轮做了什么/正在做什么/刚买了什么'"
2. 只允许三种 kind：profile、preference、fact，没有"event"类型
3. `_normalize_memory_updates()` 做二次校验：`kind not in ALLOWED_MEMORY_KINDS` 直接丢弃
4. 已有记忆作为上下文传给 LLM，让它知道哪些信息已经记住了

### Q5：如果 LLM 返回了格式错误的 JSON 怎么办？

**答题要点**：
1. `generate_json()` 本身有容错处理
2. `_normalize_memory_updates()` 对每个字段做类型检查和默认值处理
3. `kind` 不在白名单中 → 丢弃
4. `operation` 不是 upsert/delete → 默认为 upsert
5. `importance` 无法解析 → 默认 0.7
6. `content` 为空且 operation 是 upsert → 丢弃

### Q6：记忆系统的 Key 回退机制是什么？为什么需要？

**答题要点**：
1. 优先使用 LLM 提供的 key，做正则归一化
2. 如果 LLM 没有提供 key 或归一化后为空，回退到 `MD5("kind:content")[:12]`
3. 回退的意义：即使 LLM "忘记"输出 key，系统仍然能为这条记忆生成一个稳定的标识符
4. MD5 回退的局限：内容变化会导致 key 变化，所以 Prompt 中要求 LLM 必须提供稳定 key

### Q7：如何理解 `_read_dedupe_key()` 的设计？

**答题要点**：
1. 优先使用 `metadata.key` 作为去重键
2. `summary` 类型固定返回 `"summary"`（每个用户每个 Agent 只有一条摘要）
3. 其他情况回退到 `record.id`（不参与去重）
4. 这个设计保证了：有 key 的记忆按 key 去重，summary 全局唯一，无 key 的记忆各自独立

### Q8：记忆系统在多租户场景下如何隔离？

**答题要点**：
1. `MemoryRecord` 表有 `tenant_id` 字段，所有查询都带 `tenant_id` 条件
2. `user_id` 在租户内唯一，不同租户可以有相同 user_id
3. Agent 隔离是在租户+用户隔离之上的第二层
