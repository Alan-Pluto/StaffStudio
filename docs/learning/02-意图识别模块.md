## 1. 概述

StaffStudio 的意图识别不是单一模块的工作，而是**分布在整条执行链路中的分层协作**。系统通过多个阶段的 LLM 调用，逐步回答用户消息的四个核心问题。

```
用户消息
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  第一层：渠道级自动路由 (Channel Auto-Route)              │
│  ─────────────────────────────────────────────           │
│  问题：这条消息应该由哪个 Agent 处理？                     │
│  场景：一个渠道绑定了多个数字员工（如销售、客服、HR）       │
│  输出：agent_id（目标员工）或 stay（保持当前员工）          │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  第二层：轮次规划 (Turn Planner)                         │
│  ─────────────────────────────────────────────           │
│  问题：在当前 Agent 内部，这条消息应该触发什么动作？       │
│  场景：继续 SOP？切换 SOP？闲聊回复？转人工？             │
│  输出：TurnPlan（决策 + TaskFrame 执行队列）              │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  第三层：能力发现 (Harness Task Agent)                    │
│  ─────────────────────────────────────────────           │
│  问题：完成这个任务需要哪些具体能力？                      │
│  场景：调哪个工具？搜哪个知识库？读哪个技能包？            │
│  输出：HarnessAction（tool 调用或 finish）                │
└─────────────────────────────────────────────────────────┘
    │
    ▼
  执行结果 → 回复生成
```

## 2. 意图识别的四个核心问题

一个完整的 Agent 系统在面对用户消息时，需要回答四个问题。StaffStudio 将这四个问题**分散到不同的阶段**，每个阶段只回答自己擅长的问题：

### 2.1 四个问题的分工

| 问题 | 回答阶段 | 实现方式 | 关键文件 |
|------|---------|---------|---------|
| **① 用户要干什么？** | Turn Planner | LLM 提取 `user_intent` + `requirements` | `turn_planner.py` |
| **② 涉及什么业务领域？** | Turn Planner | LLM 匹配 `available_sops` → `target_skill_id` | `turn_planner.py` |
| **③ 需要哪些能力？** | Harness Task Agent | Agent 自主探索 CapabilityManifest | `harness_agent.py` |
| **④ 应该交给哪个 Agent？** | Channel Auto-Route | LLM 分类候选 Agent → `agent_id` | `service_autoroute.py` |

### 2.2 问题 ①：用户要干什么？

TurnPlanner 通过 LLM 从用户消息中提取两个关键字段：

```python
class TurnPlan(BaseModel):
    user_intent: str          # 一句话概括用户目的
    task_frames: [
        {
            "requirements": ["查询年假余额", "提交请假申请"],  # 可执行的需求列表
            "user_intent": "员工想了解年假剩余天数并提交申请",
        }
    ]
```

**`user_intent`** 是高层意图摘要，用于后续阶段理解任务目标。
**`requirements`** 是具体的、可执行的需求列表，是 Harness Agent 执行时的直接输入。

Prompt 中的约束（`turn_planner_prompt.md`）：
```
- requirements 是简短、可执行、可验证的目标列表，不是能力名称或实施方案。
- 需求边界以用户原话为准。一个有限问题原则上保持为一个 requirement；
  不得为了显得完整而自动补充用户未要求的流程阶段。
```

### 2.3 问题 ②：涉及什么业务领域？

TurnPlanner 通过将用户消息与 `available_sops`（可用 SOP 列表）进行匹配，确定业务领域：

```python
# 输入给 LLM 的 SOP 列表
"available_sops": [
    {"skill_id": "leave_request", "name": "请假申请", "description": "...", "trigger_intents": [...]},
    {"skill_id": "reimbursement", "name": "报销流程", "description": "...", "trigger_intents": [...]},
]

# LLM 输出
{
    "task_frames": [{
        "kind": "sop",
        "target_skill_id": "leave_request",  # ← 匹配到的业务领域
        "decision": "start_new_task",
    }]
}
```

**关键设计：** TurnPlanner 只匹配 SOP 级别（业务领域），不选择具体工具或知识库。如果没有匹配的 SOP，则创建 `kind="conversation"` 的 TaskFrame，由后续 Harness Agent 自主处理。

Prompt 中的约束：
```
- 判断新 SOP 时只匹配 available_sops；不要在 reason 中声称匹配了 GeneralSkill、
  知识库或 Tool。
- 没有匹配 SOP 的咨询、闲聊、计算、文件处理或其他通用需求，使用
  kind=conversation；不要伪造 SOP。
```

### 2.4 问题 ③：需要哪些能力？

**这是 TurnPlanner 明确不回答的问题。** 能力选择被推迟到 Harness Task Agent 执行阶段。

Prompt 中明确排除：
```
你不选择 GeneralSkill、知识库或 Tool，不生成工具调用，不读取 SOP 节点图，
也不生成最终回复。能力选择由后续隔离的 Harness Agent 根据每个 TaskRequirement
自主完成。
```

能力发现的过程（在 `harness_agent.py` 中）：

```
TaskRequirement（来自 TurnPlanner）
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  CapabilityManifest（能力清单）                           │
│  ├── available: [已激活、可直接调用的能力]                 │
│  ├── catalog: [紧凑目录，只有名称和描述]                   │
│  └── unavailable_references: [引用了但不可用的能力]        │
└─────────────────────────────────────────────────────────┘
    │
    ▼
Agent 自主决策循环：
    1. 查看 catalog，发现有合适能力 → 调用 capability_describe 激活
    2. catalog 不够用 → 调用 capability_search 搜索完整目录
    3. 激活后调用实际工具（HTTP/MCP/知识库/技能包）
```

**为什么这样设计？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| TurnPlanner 同时选能力 | 一次调用完成所有决策 | Prompt 过于复杂，SOP 和能力耦合，难以独立优化 |
| 当前设计（分层） | 职责清晰，TurnPlanner 只关注意图 | 增加执行阶段的工具调用次数 |

**选择分层的理由：** 能力选择需要理解 TaskRequirement 的具体细节（槽位、SOP 节点要求等），这些信息在 TurnPlanner 阶段还不完整。将能力选择推迟到执行阶段，让 Agent 根据完整的 TaskRequirement 自主决策，更灵活也更准确。

### 2.5 问题 ④：应该交给哪个 Agent？

由渠道级自动路由回答（详见第 3 节）。这是唯一在消息进入 Agent 之前就回答的问题。

### 2.6 四个问题的协作流程

```
用户消息: "帮我请明天的事假，顺便查一下我的年假还剩几天"
    │
    ▼
④ Channel Auto-Route
    → 候选: [HR助手, 财务助手, 行政助手]
    → 决策: agent_id=HR助手, confidence=0.95
    │
    ▼
① Turn Planner - 提取意图
    → user_intent: "员工想请假并查询年假余额"
    → requirements: ["请明天事假", "查询年假剩余天数"]
    │
    ▼
② Turn Planner - 匹配业务领域
    → available_sops 中有 "请假申请" SOP
    → task_frames[0]: kind="sop", target_skill_id="leave_request"
    → task_frames[1]: kind="conversation", requirements=["查询年假余额"]
    │
    ▼
③ Harness Task Agent - 能力发现（对每个 TaskFrame）
    → TaskFrame 0 (SOP): 按 SOP 节点执行，调用节点绑定的工具
    → TaskFrame 1 (conversation):
        → capability_search("年假") → 发现 knowledge_search
        → capability_describe("knowledge_search") → 激活知识库检索
        → knowledge_search("年假余额") → 获取结果
        → finish(reply_fragment="您的年假剩余...")
```

## 3. 渠道级自动路由 (service_autoroute.py)

**文件路径：** `backend/app/channels/service_autoroute.py`

### 3.1 核心目的

当一个渠道绑定（ChannelBinding）挂载了多个 Agent 时，系统需要根据用户消息的意图，自动将消息路由给最合适的 Agent 处理。

### 3.2 入口函数 `maybe_auto_route()`

这是自动路由的总入口，负责前置条件检查和粘性保护：

```python
def maybe_auto_route(
    db: Session,
    binding: ChannelBinding,
    current_agent_id: str,
    external_conv_id: str,
    message: str,
) -> RouteDecision | None:
```

**前置条件（不满足则返回 `None`，跳过分类）：**

| 条件 | 说明 |
|------|------|
| `auto_route_enabled(binding)` | 配置开关 `config_json.auto_route` 不为 `False`（默认开启） |
| `len(mounts) >= 2` | 至少挂载了 2 个 Agent，否则无需路由 |
| 非 handoff 状态 | 当前会话不处于人工转接中 |
| 无手动切换保护窗 | `manual_pin_active()` 返回 `False` |

**粘性保护机制：**

```
┌──────────────────────────────────────────────────────┐
│  粘性保护（跳过自动路由的场景）                         │
│                                                      │
│  1. handoff 进行中 → 人工接管，不自动切换              │
│  2. 手动切换保护窗 → 用户刚手动指定了员工，             │
│     短时间内不再自动干预                               │
│  3. SOP 进行中 → 不跳过，但提高置信度阈值              │
│     （0.75 → 0.9），因为会话按员工独立，               │
│     SOP 上下文在原会话中冻结可续                       │
└──────────────────────────────────────────────────────┘
```

### 3.3 分类函数 `classify_intent()`

核心分类逻辑，调用 LLM 判断意图：

```python
def classify_intent(
    db: Session,
    tenant_id: str,
    candidates: list[dict[str, Any]],
    current_agent_id: str,
    message: str,
    recent_messages: list[dict[str, str]] | None = None,
    *,
    threshold: float = AUTO_ROUTE_CONFIDENCE_THRESHOLD,
) -> RouteDecision:
```

**系统提示词：**

```python
SYSTEM_PROMPT = (
    "你是企业数字员工调度员。根据用户消息与候选员工名单，选择最合适的员工应答。\n"
    '只输出 JSON：{"agent_id": "<候选 agent_id 或 stay>", '
    '"confidence": 0到1之间的小数, "reason": "一句话原因"}。\n'
    "规则：消息意图不明确、或属于当前员工职责范围时选 stay；"
    "只有明确属于其他候选员工领域时才选该员工的 agent_id。"
)
```

**LLM 输出格式：**

```json
{
  "agent_id": "agent_hr_001",
  "confidence": 0.92,
  "reason": "用户询问年假政策，属于 HR 职责范围"
}
```

**置信度阈值：**

```python
AUTO_ROUTE_CONFIDENCE_THRESHOLD = 0.75    # 常规阈值
SOP_ACTIVE_CONFIDENCE_THRESHOLD = 0.9     # SOP 进行中（更高要求）
```

**决策流程：**

```
LLM 返回结果
    │
    ├── 解析失败 / 超时 / 异常 ──→ 回退 stay（保持当前）
    │
    ├── agent_id == "stay" 或 == current_agent_id ──→ stay
    │
    ├── agent_id 不在候选名单中 ──→ stay
    │
    ├── confidence < threshold ──→ stay
    │
    └── 通过所有检查 ──→ 切换到目标 Agent
```

### 3.4 并发安全：乐观锁（CAS）

当多个消息同时到达同一个渠道绑定时，可能出现竞态条件：两个请求都在做意图分类，但分类期间路由指针可能被另一个请求修改。系统使用 **Compare-And-Swap（CAS）乐观锁** 解决这个问题。

**核心数据结构：**

```python
# backend/app/channels/service_routing.py

class ChannelConvState:
    current_agent_id: str       # 当前路由指向的 Agent
    routing_revision: int       # 版本号（每次切换 +1）
```

**CAS 操作：**

```python
def compare_and_set_current_agent(
    db: Session,
    binding: ChannelBinding,
    external_conv_id: str,
    *,
    expected_agent_id: str,      # 期望的当前 Agent
    expected_revision: int,       # 期望的版本号
    agent_id: str,                # 要切换到的目标 Agent
) -> bool:
    """
    只有当 (current_agent_id == expected_agent_id) 
    且 (routing_revision == expected_revision) 时才更新。
    
    返回 True 表示切换成功，False 表示 CAS 失败（已被其他请求修改）。
    """
```

**为什么需要两个条件？**

| 条件 | 防护的场景 |
|------|-----------|
| `expected_agent_id` | 防止切换到错误的 Agent（比如分类期间用户手动切换了） |
| `expected_revision` | 防止 ABA 问题（Agent 从 A→B→A，版本号不同） |

**完整流程：**

```
请求 A: 读取路由状态
    → current_agent_id = "HR助手", routing_revision = 5
    │
    ▼
请求 A: 调用 LLM 分类（耗时 200ms）
    → 决策: 切换到 "财务助手"
    │
    ▼
请求 B: 在分类期间修改了路由（用户手动切换）
    → current_agent_id = "行政助手", routing_revision = 6
    │
    ▼
请求 A: 尝试 CAS 切换
    → expected: ("HR助手", 5)
    → actual:   ("行政助手", 6)
    → CAS 失败！返回 False
    │
    ▼
请求 A: 回退决策
    → decision.agent_id = "HR助手"（保持当前）
    → decision.switched = False
    → decision.error = "route_changed_during_classification"
```

**CAS 失败的处理：**

```python
# backend/app/channels/service_autoroute.py

if decision.switched:
    switched = compare_and_set_current_agent(
        db, binding, external_conv_id,
        expected_agent_id=current_agent_id,
        expected_revision=inspected_route[1],
        agent_id=decision.agent_id,
    )
    if not switched:
        # CAS 失败，回退为 stay
        decision.agent_id = current_agent_id
        decision.switched = False
        decision.error = "route_changed_during_classification"
```

**设计权衡：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| CAS 乐观锁（当前） | 无死锁，性能好，冲突少 | 冲突时需要回退 |
| 悲观锁（SELECT FOR UPDATE） | 保证成功 | 阻塞其他请求，性能差 |
| 分布式锁（Redis） | 跨进程安全 | 引入外部依赖，复杂度高 |

**选择 CAS 的理由：** 企业场景中，同一个会话的并发消息很少，CAS 冲突概率极低。即使冲突，回退为 stay 也是安全的（下次消息会重新分类）。

## 4. 轮次规划器 (turn_planner.py)

**文件路径：** `backend/app/core/turn_planner.py`

### 4.1 核心目的

在单个 Agent 内部，判断用户消息应该触发什么动作。这是 Harness v2 执行路径中的唯一意图规划点。

### 4.2 输入与输出

**`TurnPlanner.plan()` 方法签名：**

```python
class TurnPlanner:
    def plan(
        self,
        message: str,                          # 用户消息
        session: ChatSession,                  # 当前会话状态
        available_skills: list[Skill],         # 可用 SOP 列表
        model_config: ModelConfig,             # 模型配置
        conversation_context: dict | None,     # 对话上下文
        memory_context: list[dict] | None,     # 记忆上下文
        task_frame_state: list[dict] | None,   # 当前 TaskFrame 状态
        interaction_mode: str = "normal",      # 交互模式（normal/team_tl）
        team_context: TeamPlannerContext | None,  # 团队上下文
    ) -> TurnPlan:
```

**输出 `TurnPlan` 结构：**

```python
class TurnPlan(BaseModel):
    decision: RouterDecisionValue       # 顶层决策
    selected_task_id: Optional[str]     # 选中的任务 ID
    confidence: float                   # 置信度
    user_intent: Optional[str]          # 用户意图摘要
    reason: Optional[str]               # 决策原因
    clarification_question: Optional[str]  # 澄清问题
    task_frames: list[PlannedTaskFrame] # 执行队列
    task_updates: list[TaskUpdate]      # 任务更新
```

### 4.3 决策类型

| 决策 | 含义 | 场景 |
|------|------|------|
| `continue_active` | 继续当前活跃的 SOP | 用户在回答 SOP 上一步的问题 |
| `switch_to_pending` | 切换到某个挂起的任务 | 用户说"继续之前那个任务" |
| `complete_task` | 完成当前任务 | 用户确认任务完成 |
| `start_new_task` | 开始新的 SOP | 用户触发新的业务流程 |
| `answer_only` | 仅回答，不推进 SOP | 闲聊、咨询、通用问题 |
| `handoff_human` | 转人工 | 用户要求人工服务或超出能力范围 |
| `clarify` | 需要澄清 | 多个 SOP 无法区分 |

### 4.4 TaskFrame 类型

每个 `PlannedTaskFrame` 代表一个执行单元：

```python
class PlannedTaskFrame(BaseModel):
    task_id: Optional[str]              # 任务 ID
    kind: TaskFrameKind               # "sop" 或 "conversation"
    decision: RouterDecisionValue       # 该帧的决策
    target_skill_id: Optional[str]      # 目标 SOP ID
    target_step_id: Optional[str]       # 目标步骤 ID
    user_intent: Optional[str]          # 用户意图
    requirements: list[str]             # 需求列表
    slot_hints: dict[str, Any]          # 槽位提示
    depends_on_task_ids: list[str]      # 依赖的其他任务
    execution_target: str               # "self" 或 "team_member"
    assignee_agent_id: Optional[str]    # 指派的团队成员 ID
```

**两种 TaskFrame：**

| 类型 | 说明 |
|------|------|
| `kind="sop"` | SOP 执行，必须有 `target_skill_id` 来自 `available_sops` |
| `kind="conversation"` | 自由对话，不绑定 SOP，由 Harness Agent 自主选择能力 |

### 4.5 Schema 校验与修复

LLM 输出可能不符合 schema，系统提供一次修复机会：

```python
SCHEMA_REPAIR_ATTEMPTS = 1

def _generate_validated_plan(self, client, system_prompt, payload) -> TurnPlan:
    max_attempts = SCHEMA_REPAIR_ATTEMPTS + 1
    for attempt in range(max_attempts):
        raw = client.generate_json(system_prompt, next_payload)
        try:
            return TurnPlan.model_validate(raw)
        except ValidationError as exc:
            if attempt >= SCHEMA_REPAIR_ATTEMPTS:
                raise
            # 将校验错误反馈给 LLM，请求修复
            next_payload["_schema_repair"] = {
                "attempt": attempt + 1,
                "previous_output": raw,
                "validation_errors": _compact_validation_errors(exc),
                "instruction": "上一轮输出是合法 JSON，但不符合输出字段类型。"
                               "请保留原任务语义，修正列出的字段后重新输出完整 JSON object。",
            }
```

**修复流程：**

```
LLM 输出 JSON
    │
    ├── Pydantic 校验通过 ──→ 返回 TurnPlan
    │
    └── 校验失败
         │
         ├── 第一次失败 ──→ 将错误信息注入 _schema_repair，重新调用 LLM
         │
         └── 第二次仍失败 ──→ 抛出异常
```

### 4.6 归一化处理 `_normalize()`

LLM 的输出可能包含无效的 skill_id、task_id 或不一致的依赖关系，`_normalize()` 负责修正：

**主要归一化步骤：**

1. **Skill ID 校验**：验证 `target_skill_id` 是否在 `available_skills` 中
2. **Task ID 解析**：将 LLM 引用的 task_id 映射到已知的 task frame
3. **决策修正**：
   - SOP 帧的 decision 只能是 `continue_active` 或 `switch_to_pending`
   - 新 SOP 强制设为 `start_new_task`
   - conversation 帧的 decision 限制为 `answer_only`、`clarify`、`handoff_human`
4. **依赖一致性**：移除指向无效 task_id 的依赖
5. **Fallback 帧生成**：当 LLM 输出空 task_frames 时，根据 decision 生成兜底帧

**Fallback 逻辑示例：**

```python
if not frames:
    if plan.decision == "continue_active" and active_skill is not None:
        # 生成继续当前 SOP 的帧
        frames.append(PlannedTaskFrame(
            kind="sop",
            decision="continue_active",
            target_skill_id=active_skill.skill_id,
            target_step_id=session.active_step_id or _first_node_id(active_skill),
            ...
        ))
    elif plan.decision == "handoff_human":
        # 生成转人工帧
        ...
    else:
        # 生成 conversation 帧
        frames.append(PlannedTaskFrame(
            kind="conversation",
            decision="answer_only",
            ...
        ))
```

### 4.7 执行目标归一化

团队模式下，需要验证 LLM 指派的团队成员是否有效：

```python
def _normalize_execution_targets(
    frames: list[PlannedTaskFrame],
    *,
    interaction_mode: str,
    team_context: TeamPlannerContext | None,
) -> list[PlannedTaskFrame]:
```

**规则：**

| 条件 | 处理 |
|------|------|
| `interaction_mode == "team_tl"` 且 assignee 在成员列表中 | 保持 `execution_target="team_member"` |
| 其他情况 | 回退为 `execution_target="self"`，清空 assignee |
| 远程任务依赖本地任务 | 将远程任务降级为本地（防止永久阻塞） |

## 5. TaskFrame 深度解析

### 5.1 什么是 TaskFrame？

TaskFrame 是 Harness v2 引擎中的**核心执行单元**。它将用户的一轮消息拆解为多个可独立执行、可并行、可依赖的任务帧。

**类比理解：**

| 概念 | 类比 | 说明 |
|------|------|------|
| TurnPlan | 项目经理的排期计划 | 决定"做什么、什么顺序、谁来做" |
| TaskFrame | 具体的工作任务单 | 每个任务有明确目标、依赖关系、执行者 |
| HarnessTaskAgent | 执行任务的工程师 | 根据任务单自主决定如何完成 |

### 5.2 TaskFrame 的生命周期

```
TurnPlanner 创建 PlannedTaskFrame
    │
    ▼
TaskFrameStore 持久化为 HarnessTaskFrameRecord
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  状态机                                                  │
│                                                          │
│  queued ──→ running ──→ completed                        │
│     │         │                                          │
│     │         ├──→ awaiting_user（等待用户输入）          │
│     │         │         │                                │
│     │         │         └──→ running（用户回复后继续）    │
│     │         │                                          │
│     │         ├──→ handoff（转人工）                      │
│     │         │                                          │
│     │         ├──→ blocked（等待依赖）                    │
│     │         │         │                                │
│     │         │         └──→ running（依赖完成后继续）    │
│     │         │                                          │
│     │         └──→ failed（执行失败）                     │
│     │                                                    │
│     └──→ cancelled（被取消）                              │
└─────────────────────────────────────────────────────────┘
```

### 5.3 TaskFrame 的两种类型

| 类型 | 说明 | 执行方式 |
|------|------|---------|
| `kind="sop"` | SOP 执行帧 | 按 SOP 图的节点和边逐步执行，每个节点有明确的指令和允许动作 |
| `kind="conversation"` | 自由对话帧 | Harness Agent 自主选择能力（工具、知识库、技能包）完成任务 |

**示例：**

```python
# 用户说："帮我请明天的事假，顺便查一下我的年假还剩几天"

task_frames = [
    PlannedTaskFrame(
        task_id="task_001",
        kind="sop",                          # SOP 执行
        target_skill_id="leave_request",     # 匹配到"请假申请" SOP
        decision="start_new_task",
        requirements=["请明天事假"],
    ),
    PlannedTaskFrame(
        task_id="task_002",
        kind="conversation",                 # 自由对话
        requirements=["查询年假剩余天数"],    # Agent 自主决定如何查询
    ),
]
```

### 5.4 TaskFrame 的依赖关系

TaskFrame 之间可以通过 `depends_on_task_ids` 建立执行顺序：

```python
# 用户说："先帮我查一下年假余额，然后根据余额决定请几天假"

task_frames = [
    PlannedTaskFrame(
        task_id="task_query",
        kind="conversation",
        requirements=["查询年假剩余天数"],
        depends_on_task_ids=[],              # 无依赖，先执行
    ),
    PlannedTaskFrame(
        task_id="task_leave",
        kind="sop",
        target_skill_id="leave_request",
        requirements=["根据年假余额决定请假天数并提交申请"],
        depends_on_task_ids=["task_query"],  # 依赖查询结果
    ),
]
```

**依赖检查逻辑：**

```python
# backend/app/core/task_frame_store.py

def dependencies_satisfied(self, frame: HarnessTaskFrameRecord) -> bool:
    """检查所有依赖的 TaskFrame 是否已完成。"""
    for dep_id in frame.depends_on_task_ids_json or []:
        dep = self.db.get(HarnessTaskFrameRecord, dep_id)
        if not dep or dep.status != "completed":
            return False
    return True
```

### 5.5 TaskFrame 的执行目标

在团队协作模式下，TaskFrame 可以指定执行者：

| `execution_target` | 说明 | 执行方式 |
|-------------------|------|---------|
| `"self"` | 本地执行 | 当前 Agent 自己执行 |
| `"team_member"` | 远程执行 | 分配给团队成员 Agent 执行 |

**示例（团队 TL 模式）：**

```python
# TL 收到用户请求："帮我写一份报告，同时查一下最新的市场数据"

task_frames = [
    PlannedTaskFrame(
        task_id="task_write",
        kind="conversation",
        requirements=["撰写季度报告"],
        execution_target="team_member",
        assignee_agent_id="agent_writer",  # 分配给"写手" Agent
    ),
    PlannedTaskFrame(
        task_id="task_research",
        kind="conversation",
        requirements=["查询最新市场数据"],
        execution_target="team_member",
        assignee_agent_id="agent_researcher",  # 分配给"研究员" Agent
    ),
]
```

### 5.6 TaskFrame 与 TaskRequirement 的关系

TaskFrame 是**规划层**的概念，TaskRequirement 是**执行层**的概念：

```
PlannedTaskFrame（TurnPlanner 输出）
    │
    ▼
TaskFrameStore 持久化
    │
    ▼
TaskRequestCompiler.compile()
    │
    ▼
TaskRequirement（HarnessTaskAgent 输入）
    │
    ├── goal: "完成请假申请 SOP 的当前步骤"
    ├── requirements: ["请明天事假"]
    ├── required_slots: ["start_date", "end_date", "reason"]
    ├── known_slots: {"start_date": "2026-03-01"}
    ├── capability_manifest: [可用工具、知识库、技能包]
    ├── completion_criteria: ["收集并确认所有必填字段"]
    └── allowed_transitions: [SOP 图的边]
```

**关键区别：**

| 维度 | TaskFrame | TaskRequirement |
|------|-----------|-----------------|
| 产生阶段 | TurnPlanner（规划） | TaskRequestCompiler（编译） |
| 职责 | 定义"做什么" | 定义"怎么做"的边界 |
| 包含能力信息？ | 否 | 是（capability_manifest） |
| 包含 SOP 上下文？ | 仅 skill_id 和 step_id | 完整节点信息、允许转换 |
| 持久化？ | 是（HarnessTaskFrameRecord） | 否（内存中传递给 Agent） |

## 7. 设计决策与权衡

### 7.1 为什么使用 LLM 而非传统分类器？

| 维度 | 传统分类器 | LLM 分类 |
|------|-----------|---------|
| 新意图处理 | 需要重新训练 | 零样本泛化 |
| 上下文理解 | 有限 | 可理解复杂上下文 |
| 灵活性 | 固定类别 | 动态推理 |
| 延迟 | 低（ms 级） | 较高（100ms+） |
| 成本 | 低 | 较高 |

**选择 LLM 的理由：** 企业场景意图多样且持续变化，LLM 的灵活性比传统分类器更适合。

### 7.2 置信度阈值设计

```
常规场景：threshold = 0.75
    └── 平衡准确性和切换频率

SOP 进行中：threshold = 0.9
    └── 更高要求，因为切换会中断当前流程
    └── 会话按员工独立，原 SOP 上下文冻结可续，不会丢失
```

**调优方法：** 通过 `record_auto_route_event()` 记录每次决策，后续可分析误判案例调整阈值。

### 7.3 Fallback 策略

**核心原则：任何失败都回退到"保持当前"，绝不抛错。**

```
失败类型                 处理方式
─────────────────────────────────────────
LLM 超时                 stay（保持当前 Agent）
JSON 解析失败            stay
置信度过低               stay
目标不在候选名单         stay
CAS 并发冲突             stay
缺少模型配置             stay
```

**理由：** 在企业场景中，消息处理中断比偶尔路由错误的体验更差。

### 7.4 单次 LLM 调用

TurnPlanner 在一次调用中完成：
1. 意图判断
2. TaskFrame 拆分
3. 依赖关系建立

**权衡：** 虽然可以拆成多次调用（先判断意图，再拆分任务），但单次调用减少了延迟和 token 消耗。

### 7.5 Schema 修复 vs 严格拒绝

| 策略 | 优点 | 缺点 |
|------|------|------|
| 严格拒绝 | 简单 | 用户体验差，需要用户重试 |
| 一次修复 | 容错性好 | 增加一次 LLM 调用 |
| 无限重试 | 高成功率 | 延迟不可控，成本上升 |

**选择一次修复：** 平衡容错性和延迟。

### 7.6 两层路由 vs 单层路由

```
方案 A：单层路由
    用户消息 → LLM → 同时决定 Agent 和动作
    问题：职责混杂，prompt 复杂，难以独立优化

方案 B：两层路由（当前设计）
    用户消息 → 渠道路由 LLM → Agent 内规划 LLM
    优点：职责清晰，可独立迭代，fallback 更简单
```

## 8. 面试题

### Q1: 这个系统的意图识别是如何工作的？

**答：** 系统采用两层意图识别架构：

1. **渠道级自动路由**：当消息到达时，首先判断应该由哪个 Agent 处理。使用 LLM 根据用户消息和候选 Agent 列表进行分类，输出目标 `agent_id` 和置信度。只有置信度超过阈值（0.75 或 0.9）且目标在候选名单中时才切换。

2. **轮次规划**：消息到达目标 Agent 后，TurnPlanner 判断应该执行什么动作（继续 SOP、切换任务、闲聊回复、转人工等），并生成 TaskFrame 执行队列。

两层都使用 LLM，但职责完全隔离，可独立优化。

### Q2: 渠道级路由和轮次规划有什么区别？

**答：**

| 维度 | 渠道级路由 | 轮次规划 |
|------|-----------|---------|
| 解决的问题 | 谁来处理 | 做什么 |
| 输入 | 用户消息 + 候选 Agent 列表 | 用户消息 + 会话状态 + 可用 SOP |
| 输出 | agent_id + confidence | TurnPlan（决策 + TaskFrames） |
| 调用时机 | 消息进入渠道时 | 消息到达 Agent 后 |
| 文件 | `service_autoroute.py` | `turn_planner.py` |

### Q3: 如何处理 LLM 输出校验？

**答：** 采用 Pydantic + 一次修复策略：

1. LLM 输出 JSON 后，用 `TurnPlan.model_validate()` 校验
2. 校验失败时，将错误信息（路径、类型、消息）注入 `_schema_repair` 字段
3. 重新调用 LLM，要求修复指定字段
4. 第二次仍失败则抛出异常

```python
next_payload["_schema_repair"] = {
    "validation_errors": _compact_validation_errors(exc),
    "instruction": "请保留原任务语义，修正列出的字段后重新输出。",
}
```

### Q4: LLM 调用失败时会发生什么？

**答：** 所有失败都回退到"保持当前状态"，绝不中断对话：

- **渠道路由失败**：返回 `stay`，继续使用当前 Agent
- **TurnPlanner 失败**：抛出 `LLMError`，由上层处理（通常也是保持当前状态）

关键代码：

```python
def classify_intent(...):
    stay = RouteDecision(agent_id=current_agent_id, switched=False, ...)
    try:
        text = LLMClient(model_config).generate_text(...)
        data = json.loads(text)
        # ... 解析逻辑
    except Exception as exc:
        logger.warning("智能分发分类失败，保持当前员工: %s", exc)
        stay.error = str(exc)[:200]
        return stay  # 永远返回 stay，不抛错
```

### Q5: 如何防止路由循环？

**答：** 多层防护：

1. **粘性保护**：手动切换后有保护窗，短时间内不再自动路由
2. **Handoff 状态**：人工转接中完全跳过自动路由
3. **CAS 乐观锁**：切换时检查 revision，防止并发修改导致循环
4. **高阈值**：SOP 进行中要求 0.9 置信度，减少误切换

```python
# 粘性保护检查
if current_session and current_session.status == "handoff":
    return None
if manual_pin_active(db, binding, external_conv_id):
    return None
```

### Q6: 置信度阈值是如何调优的？

**答：** 基于业务场景分层设置：

| 场景 | 阈值 | 理由 |
|------|------|------|
| 常规 | 0.75 | 平衡准确性和切换频率 |
| SOP 进行中 | 0.9 | 切换会中断流程，需要更高确定性 |

调优方法：
1. 通过 `record_auto_route_event()` 记录每次决策的 confidence、threshold、switched
2. 分析误判案例（该切没切、不该切切了）
3. 根据业务反馈调整阈值

### Q7: 为什么 TurnPlanner 要拆成 TaskFrame？

**答：** TaskFrame 设计解决三个问题：

1. **多任务并行**：用户可能一句话包含多个需求，拆成独立帧可并行执行
2. **依赖管理**：通过 `depends_on_task_ids` 建立执行顺序
3. **团队协作**：通过 `execution_target` 区分本地任务和远程任务（分配给团队成员）

```python
# 示例：用户说"帮我请假，然后查一下余额"
task_frames = [
    PlannedTaskFrame(kind="sop", target_skill_id="leave_request", ...),
    PlannedTaskFrame(kind="conversation", requirements=["查询余额"], ...),
]
```

### Q8: 如何处理 LLM 幻觉（如编造不存在的 skill_id）？

**答：** `_normalize()` 方法做多层校验：

1. **Skill ID 校验**：`target_skill_id` 必须在 `available_skills` 中
2. **Task ID 映射**：LLM 引用的 task_id 必须在已知 frames 中
3. **Fallback 生成**：无效帧被丢弃后，根据 decision 生成兜底帧

```python
if not frame.target_skill_id or frame.target_skill_id not in skills:
    continue  # 丢弃无效 SOP 帧

# 最终如果没有有效帧，生成 fallback
if not frames:
    frames.append(PlannedTaskFrame(
        kind="conversation",
        decision="answer_only",
        ...
    ))
```
