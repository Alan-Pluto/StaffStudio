## 1. 概述

StaffStudio 的意图识别分为两个层级，分别解决不同的路由问题：

```
用户消息
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  第一层：渠道级自动路由 (Channel Auto-Route)              │
│  ─────────────────────────────────────────────           │
│  问题：这条消息应该由哪个 Agent 处理？                     │
│  场景：一个渠道绑定了多个数字员工（如销售、客服、HR）       │
│  输出：agent_id（目标员工）或 stay（保持当前员工）          │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  第二层：轮次规划 (Turn Planner)                         │
│  ─────────────────────────────────────────────           │
│  问题：在当前 Agent 内部，这条消息应该触发什么动作？       │
│  场景：继续 SOP？切换 SOP？闲聊回复？转人工？             │
│  输出：TurnPlan（决策 + TaskFrame 执行队列）              │
└─────────────────────────────────────────────────────────┘
    │
    ▼
  执行层（Harness Agent）
```

两层都使用 LLM 做分类，但职责完全隔离：第一层只选"谁来做"，第二层只决定"做什么"。

## 2. 渠道级自动路由 (service_autoroute.py)

**文件路径：** `backend/app/channels/service_autoroute.py`

### 2.1 核心目的

当一个渠道绑定（ChannelBinding）挂载了多个 Agent 时，系统需要根据用户消息的意图，自动将消息路由给最合适的 Agent 处理。

### 2.2 入口函数 `maybe_auto_route()`

这是自动路由的总入口，负责前置条件检查和粘性保护：

```python
def maybe_auto_route(
    db: Session,
    binding: ChannelBinding,
    current_agent_id: str,
    external_conv_id: str,
    message: str,
) -> RouteDecision | None:
```

**前置条件（不满足则返回 `None`，跳过分类）：**

| 条件 | 说明 |
|------|------|
| `auto_route_enabled(binding)` | 配置开关 `config_json.auto_route` 不为 `False`（默认开启） |
| `len(mounts) >= 2` | 至少挂载了 2 个 Agent，否则无需路由 |
| 非 handoff 状态 | 当前会话不处于人工转接中 |
| 无手动切换保护窗 | `manual_pin_active()` 返回 `False` |

**粘性保护机制：**

```
┌──────────────────────────────────────────────────────┐
│  粘性保护（跳过自动路由的场景）                         │
│                                                      │
│  1. handoff 进行中 → 人工接管，不自动切换              │
│  2. 手动切换保护窗 → 用户刚手动指定了员工，             │
│     短时间内不再自动干预                               │
│  3. SOP 进行中 → 不跳过，但提高置信度阈值              │
│     （0.75 → 0.9），因为会话按员工独立，               │
│     SOP 上下文在原会话中冻结可续                       │
└──────────────────────────────────────────────────────┘
```

### 2.3 分类函数 `classify_intent()`

核心分类逻辑，调用 LLM 判断意图：

```python
def classify_intent(
    db: Session,
    tenant_id: str,
    candidates: list[dict[str, Any]],
    current_agent_id: str,
    message: str,
    recent_messages: list[dict[str, str]] | None = None,
    *,
    threshold: float = AUTO_ROUTE_CONFIDENCE_THRESHOLD,
) -> RouteDecision:
```

**系统提示词：**

```python
SYSTEM_PROMPT = (
    "你是企业数字员工调度员。根据用户消息与候选员工名单，选择最合适的员工应答。\n"
    '只输出 JSON：{"agent_id": "<候选 agent_id 或 stay>", '
    '"confidence": 0到1之间的小数, "reason": "一句话原因"}。\n'
    "规则：消息意图不明确、或属于当前员工职责范围时选 stay；"
    "只有明确属于其他候选员工领域时才选该员工的 agent_id。"
)
```

**LLM 输出格式：**

```json
{
  "agent_id": "agent_hr_001",
  "confidence": 0.92,
  "reason": "用户询问年假政策，属于 HR 职责范围"
}
```

**置信度阈值：**

```python
AUTO_ROUTE_CONFIDENCE_THRESHOLD = 0.75    # 常规阈值
SOP_ACTIVE_CONFIDENCE_THRESHOLD = 0.9     # SOP 进行中（更高要求）
```

**决策流程：**

```
LLM 返回结果
    │
    ├── 解析失败 / 超时 / 异常 ──→ 回退 stay（保持当前）
    │
    ├── agent_id == "stay" 或 == current_agent_id ──→ stay
    │
    ├── agent_id 不在候选名单中 ──→ stay
    │
    ├── confidence < threshold ──→ stay
    │
    └── 通过所有检查 ──→ 切换到目标 Agent
```

### 2.4 并发安全：乐观锁

切换路由指针时使用 `compare_and_set_current_agent()` 实现乐观并发控制：

```python
def compare_and_set_current_agent(
    db: Session,
    binding: ChannelBinding,
    external_conv_id: str,
    *,
    expected_agent_id: str,
    expected_revision: int,
    agent_id: str,
) -> bool:
```

原理：只在 `current_agent_id` 和 `routing_revision` 都与预期一致时才更新，防止分类期间路由被其他请求修改。若 CAS 失败，决策回退为 stay。

RECENT_MESSAGE_CHAR_LIMIT = 200

每次决策都会落事件日志，便于观测和复盘：

## 3. 轮次规划器 (turn_planner.py)

**文件路径：** `backend/app/core/turn_planner.py`

### 3.1 核心目的

在单个 Agent 内部，判断用户消息应该触发什么动作。这是 Harness v2 执行路径中的唯一意图规划点。

### 3.2 输入与输出

**`TurnPlanner.plan()` 方法签名：**

```python
class TurnPlanner:
    def plan(
        self,
        message: str,                          # 用户消息
        session: ChatSession,                  # 当前会话状态
        available_skills: list[Skill],         # 可用 SOP 列表
        model_config: ModelConfig,             # 模型配置
        conversation_context: dict | None,     # 对话上下文
        memory_context: list[dict] | None,     # 记忆上下文
        task_frame_state: list[dict] | None,   # 当前 TaskFrame 状态
        interaction_mode: str = "normal",      # 交互模式（normal/team_tl）
        team_context: TeamPlannerContext | None,  # 团队上下文
    ) -> TurnPlan:
```

**输出 `TurnPlan` 结构：**

```python
class TurnPlan(BaseModel):
    decision: RouterDecisionValue       # 顶层决策
    selected_task_id: Optional[str]     # 选中的任务 ID
    confidence: float                   # 置信度
    user_intent: Optional[str]          # 用户意图摘要
    reason: Optional[str]               # 决策原因
    clarification_question: Optional[str]  # 澄清问题
    task_frames: list[PlannedTaskFrame] # 执行队列
    task_updates: list[TaskUpdate]      # 任务更新
```

### 3.3 决策类型

| 决策 | 含义 | 场景 |
|------|------|------|
| `continue_active` | 继续当前活跃的 SOP | 用户在回答 SOP 上一步的问题 |
| `switch_to_pending` | 切换到某个挂起的任务 | 用户说"继续之前那个任务" |
| `complete_task` | 完成当前任务 | 用户确认任务完成 |
| `start_new_task` | 开始新的 SOP | 用户触发新的业务流程 |
| `answer_only` | 仅回答，不推进 SOP | 闲聊、咨询、通用问题 |
| `handoff_human` | 转人工 | 用户要求人工服务或超出能力范围 |
| `clarify` | 需要澄清 | 多个 SOP 无法区分 |

### 3.4 TaskFrame 类型

每个 `PlannedTaskFrame` 代表一个执行单元：

```python
class PlannedTaskFrame(BaseModel):
    task_id: Optional[str]              # 任务 ID
    kind: TaskFrameKind               # "sop" 或 "conversation"
    decision: RouterDecisionValue       # 该帧的决策
    target_skill_id: Optional[str]      # 目标 SOP ID
    target_step_id: Optional[str]       # 目标步骤 ID
    user_intent: Optional[str]          # 用户意图
    requirements: list[str]             # 需求列表
    slot_hints: dict[str, Any]          # 槽位提示
    depends_on_task_ids: list[str]      # 依赖的其他任务
    execution_target: str               # "self" 或 "team_member"
    assignee_agent_id: Optional[str]    # 指派的团队成员 ID
```

**两种 TaskFrame：**

| 类型 | 说明 |
|------|------|
| `kind="sop"` | SOP 执行，必须有 `target_skill_id` 来自 `available_sops` |
| `kind="conversation"` | 自由对话，不绑定 SOP，由 Harness Agent 自主选择能力 |

### 3.5 Schema 校验与修复

LLM 输出可能不符合 schema，系统提供一次修复机会：

```python
SCHEMA_REPAIR_ATTEMPTS = 1

def _generate_validated_plan(self, client, system_prompt, payload) -> TurnPlan:
    max_attempts = SCHEMA_REPAIR_ATTEMPTS + 1
    for attempt in range(max_attempts):
        raw = client.generate_json(system_prompt, next_payload)
        try:
            return TurnPlan.model_validate(raw)
        except ValidationError as exc:
            if attempt >= SCHEMA_REPAIR_ATTEMPTS:
                raise
            # 将校验错误反馈给 LLM，请求修复
            next_payload["_schema_repair"] = {
                "attempt": attempt + 1,
                "previous_output": raw,
                "validation_errors": _compact_validation_errors(exc),
                "instruction": "上一轮输出是合法 JSON，但不符合输出字段类型。"
                               "请保留原任务语义，修正列出的字段后重新输出完整 JSON object。",
            }
```

**修复流程：**

```
LLM 输出 JSON
    │
    ├── Pydantic 校验通过 ──→ 返回 TurnPlan
    │
    └── 校验失败
         │
         ├── 第一次失败 ──→ 将错误信息注入 _schema_repair，重新调用 LLM
         │
         └── 第二次仍失败 ──→ 抛出异常
```

### 3.6 归一化处理 `_normalize()`

LLM 的输出可能包含无效的 skill_id、task_id 或不一致的依赖关系，`_normalize()` 负责修正：

**主要归一化步骤：**

1. **Skill ID 校验**：验证 `target_skill_id` 是否在 `available_skills` 中
2. **Task ID 解析**：将 LLM 引用的 task_id 映射到已知的 task frame
3. **决策修正**：
   - SOP 帧的 decision 只能是 `continue_active` 或 `switch_to_pending`
   - 新 SOP 强制设为 `start_new_task`
   - conversation 帧的 decision 限制为 `answer_only`、`clarify`、`handoff_human`
4. **依赖一致性**：移除指向无效 task_id 的依赖
5. **Fallback 帧生成**：当 LLM 输出空 task_frames 时，根据 decision 生成兜底帧

**Fallback 逻辑示例：**

```python
if not frames:
    if plan.decision == "continue_active" and active_skill is not None:
        # 生成继续当前 SOP 的帧
        frames.append(PlannedTaskFrame(
            kind="sop",
            decision="continue_active",
            target_skill_id=active_skill.skill_id,
            target_step_id=session.active_step_id or _first_node_id(active_skill),
            ...
        ))
    elif plan.decision == "handoff_human":
        # 生成转人工帧
        ...
    else:
        # 生成 conversation 帧
        frames.append(PlannedTaskFrame(
            kind="conversation",
            decision="answer_only",
            ...
        ))
```

### 3.7 执行目标归一化

团队模式下，需要验证 LLM 指派的团队成员是否有效：

```python
def _normalize_execution_targets(
    frames: list[PlannedTaskFrame],
    *,
    interaction_mode: str,
    team_context: TeamPlannerContext | None,
) -> list[PlannedTaskFrame]:
```

**规则：**

| 条件 | 处理 |
|------|------|
| `interaction_mode == "team_tl"` 且 assignee 在成员列表中 | 保持 `execution_target="team_member"` |
| 其他情况 | 回退为 `execution_target="self"`，清空 assignee |
| 远程任务依赖本地任务 | 将远程任务降级为本地（防止永久阻塞） |

### 4.3 Prompt 文件

**文件路径：** `backend/app/llm/prompts/turn_planner_prompt.md`

核心约束（节选）：

```markdown
你是 Turn Planner，也是对话执行内核中唯一负责意图和 SOP 状态规划的模型阶段。

你的职责只有：
1. 判断当前消息是否继续、切换、开始、完成或暂不推进某个 SOP。
2. 将本轮需要执行的工作拆成有顺序的 TaskFrame。
3. 把用户在同一句话中的附加需求完整保留到对应 TaskFrame.requirements。

你不选择 GeneralSkill、知识库或 Tool，不生成工具调用，不读取 SOP 节点图，
也不生成最终回复。
```

**关键设计原则：**

- 职责单一：只规划意图，不选择具体能力
- 能力选择后置：由后续 Harness Agent 根据 TaskRequirement 自主完成
- 需求边界以用户原话为准，不自动扩展

## 5. 设计决策与权衡

### 5.1 为什么使用 LLM 而非传统分类器？

| 维度 | 传统分类器 | LLM 分类 |
|------|-----------|---------|
| 新意图处理 | 需要重新训练 | 零样本泛化 |
| 上下文理解 | 有限 | 可理解复杂上下文 |
| 灵活性 | 固定类别 | 动态推理 |
| 延迟 | 低（ms 级） | 较高（100ms+） |
| 成本 | 低 | 较高 |

**选择 LLM 的理由：** 企业场景意图多样且持续变化，LLM 的灵活性比传统分类器更适合。

### 5.2 置信度阈值设计

```
常规场景：threshold = 0.75
    └── 平衡准确性和切换频率

SOP 进行中：threshold = 0.9
    └── 更高要求，因为切换会中断当前流程
    └── 会话按员工独立，原 SOP 上下文冻结可续，不会丢失
```

**调优方法：** 通过 `record_auto_route_event()` 记录每次决策，后续可分析误判案例调整阈值。

### 5.3 Fallback 策略

**核心原则：任何失败都回退到"保持当前"，绝不抛错。**

```
失败类型                 处理方式
─────────────────────────────────────────
LLM 超时                 stay（保持当前 Agent）
JSON 解析失败            stay
置信度过低               stay
目标不在候选名单         stay
CAS 并发冲突             stay
缺少模型配置             stay
```

**理由：** 在企业场景中，消息处理中断比偶尔路由错误的体验更差。

### 5.4 单次 LLM 调用

TurnPlanner 在一次调用中完成：
1. 意图判断
2. TaskFrame 拆分
3. 依赖关系建立

**权衡：** 虽然可以拆成多次调用（先判断意图，再拆分任务），但单次调用减少了延迟和 token 消耗。

### 5.5 Schema 修复 vs 严格拒绝

| 策略 | 优点 | 缺点 |
|------|------|------|
| 严格拒绝 | 简单 | 用户体验差，需要用户重试 |
| 一次修复 | 容错性好 | 增加一次 LLM 调用 |
| 无限重试 | 高成功率 | 延迟不可控，成本上升 |

**选择一次修复：** 平衡容错性和延迟。

### 5.6 两层路由 vs 单层路由

```
方案 A：单层路由
    用户消息 → LLM → 同时决定 Agent 和动作
    问题：职责混杂，prompt 复杂，难以独立优化

方案 B：两层路由（当前设计）
    用户消息 → 渠道路由 LLM → Agent 内规划 LLM
    优点：职责清晰，可独立迭代，fallback 更简单
```

## 6. 面试题

### Q1: 这个系统的意图识别是如何工作的？

**答：** 系统采用两层意图识别架构：

1. **渠道级自动路由**：当消息到达时，首先判断应该由哪个 Agent 处理。使用 LLM 根据用户消息和候选 Agent 列表进行分类，输出目标 `agent_id` 和置信度。只有置信度超过阈值（0.75 或 0.9）且目标在候选名单中时才切换。

2. **轮次规划**：消息到达目标 Agent 后，TurnPlanner 判断应该执行什么动作（继续 SOP、切换任务、闲聊回复、转人工等），并生成 TaskFrame 执行队列。

两层都使用 LLM，但职责完全隔离，可独立优化。

### Q2: 渠道级路由和轮次规划有什么区别？

**答：**

| 维度 | 渠道级路由 | 轮次规划 |
|------|-----------|---------|
| 解决的问题 | 谁来处理 | 做什么 |
| 输入 | 用户消息 + 候选 Agent 列表 | 用户消息 + 会话状态 + 可用 SOP |
| 输出 | agent_id + confidence | TurnPlan（决策 + TaskFrames） |
| 调用时机 | 消息进入渠道时 | 消息到达 Agent 后 |
| 文件 | `service_autoroute.py` | `turn_planner.py` |

### Q3: 如何处理 LLM 输出校验？

**答：** 采用 Pydantic + 一次修复策略：

1. LLM 输出 JSON 后，用 `TurnPlan.model_validate()` 校验
2. 校验失败时，将错误信息（路径、类型、消息）注入 `_schema_repair` 字段
3. 重新调用 LLM，要求修复指定字段
4. 第二次仍失败则抛出异常

```python
next_payload["_schema_repair"] = {
    "validation_errors": _compact_validation_errors(exc),
    "instruction": "请保留原任务语义，修正列出的字段后重新输出。",
}
```

### Q4: LLM 调用失败时会发生什么？

**答：** 所有失败都回退到"保持当前状态"，绝不中断对话：

- **渠道路由失败**：返回 `stay`，继续使用当前 Agent
- **TurnPlanner 失败**：抛出 `LLMError`，由上层处理（通常也是保持当前状态）

关键代码：

```python
def classify_intent(...):
    stay = RouteDecision(agent_id=current_agent_id, switched=False, ...)
    try:
        text = LLMClient(model_config).generate_text(...)
        data = json.loads(text)
        # ... 解析逻辑
    except Exception as exc:
        logger.warning("智能分发分类失败，保持当前员工: %s", exc)
        stay.error = str(exc)[:200]
        return stay  # 永远返回 stay，不抛错
```

### Q5: 如何防止路由循环？

**答：** 多层防护：

1. **粘性保护**：手动切换后有保护窗，短时间内不再自动路由
2. **Handoff 状态**：人工转接中完全跳过自动路由
3. **CAS 乐观锁**：切换时检查 revision，防止并发修改导致循环
4. **高阈值**：SOP 进行中要求 0.9 置信度，减少误切换

```python
# 粘性保护检查
if current_session and current_session.status == "handoff":
    return None
if manual_pin_active(db, binding, external_conv_id):
    return None
```

### Q6: 置信度阈值是如何调优的？

**答：** 基于业务场景分层设置：

| 场景 | 阈值 | 理由 |
|------|------|------|
| 常规 | 0.75 | 平衡准确性和切换频率 |
| SOP 进行中 | 0.9 | 切换会中断流程，需要更高确定性 |

调优方法：
1. 通过 `record_auto_route_event()` 记录每次决策的 confidence、threshold、switched
2. 分析误判案例（该切没切、不该切切了）
3. 根据业务反馈调整阈值

### Q7: 为什么 TurnPlanner 要拆成 TaskFrame？

**答：** TaskFrame 设计解决三个问题：

1. **多任务并行**：用户可能一句话包含多个需求，拆成独立帧可并行执行
2. **依赖管理**：通过 `depends_on_task_ids` 建立执行顺序
3. **团队协作**：通过 `execution_target` 区分本地任务和远程任务（分配给团队成员）

```python
# 示例：用户说"帮我请假，然后查一下余额"
task_frames = [
    PlannedTaskFrame(kind="sop", target_skill_id="leave_request", ...),
    PlannedTaskFrame(kind="conversation", requirements=["查询余额"], ...),
]
```

### Q8: 如何处理 LLM 幻觉（如编造不存在的 skill_id）？

**答：** `_normalize()` 方法做多层校验：

1. **Skill ID 校验**：`target_skill_id` 必须在 `available_skills` 中
2. **Task ID 映射**：LLM 引用的 task_id 必须在已知 frames 中
3. **Fallback 生成**：无效帧被丢弃后，根据 decision 生成兜底帧

```python
if not frame.target_skill_id or frame.target_skill_id not in skills:
    continue  # 丢弃无效 SOP 帧

# 最终如果没有有效帧，生成 fallback
if not frames:
    frames.append(PlannedTaskFrame(
        kind="conversation",
        decision="answer_only",
        ...
    ))
```
